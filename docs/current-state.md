# KickMate 현재 구현 상태

이 문서는 현재 코드가 실제로 제공하는 기능과 아직 연결되지 않은 부분을 기록한다. 구조적 원칙은 [architecture.md](./architecture.md)를 참고한다.

마지막 확인일: 2026-08-17

## 요약

현재 KickMate는 게임 규칙을 실행하고 최선 수를 탐색할 수 있는 엔진 골격이 완성된 상태다. 브라우저는 초기 보드와 기물을 한 번 그릴 수 있지만, 사용자가 수를 두고 봇과 경기를 진행하는 대국 루프는 아직 없다.

```text
저장소 골격             완료
순수 룰 엔진            완료
Lv.1 평가와 수 탐색     완료
Worker 어댑터           작성됨, 클라이언트 미연결
초기 Canvas 렌더링      부분 구현
사용자 입력과 턴 진행   미구현
봇 대국                 미구현
퍼즐 실행·검산          미구현
셀프플레이              미구현
```

## 구현된 기능

### 엔진 데이터 모델

`src/engine/types.ts`에 다음 타입이 정의돼 있다.

- 13×9 보드 크기
- `home | away` 팀
- GK, DF, MF, FW 역할
- 기물 ID, 팀, 역할, 좌표
- 소유 중인 공과 루즈볼
- 턴, 최대 턴, 기물, 공, 스틸 보호, 점수로 구성된 `GameState`
- 이동, 패스, 슛, 스틸로 구성된 `Move`
- 최선 수와 루트 후보 점수를 포함하는 `SearchResult`

### 초기 상태와 킥오프

`src/engine/rules.ts`의 `createInitialState()`가 다음 상태를 생성한다.

- home 4기물, away 4기물
- 양 팀 GK, DF, MF, FW 각 1명
- 프로토타입과 같은 미러 배치
- home MF가 센터 `(6,4)`에서 공 소유
- 점수 0:0
- home 선공
- 최대 60 ply

득점 후에는 모든 기물이 초기 배치로 돌아가고 실점 팀 MF가 센터에서 킥오프한다.

### 합법 수 생성

`legalMoves()`가 현재 팀의 가능한 수를 결정론적으로 생성한다.

- GK: 골키퍼 박스 안 8방향 1칸
- DF: 상하좌우 최대 2칸 슬라이드
- MF: 8방향 최대 2칸 슬라이드
- FW: 나이트 점프
- 소유자의 8방향 최대 6칸 패스
- 골라인까지 최대 7칸인 슛
- 상대 소유자와 맨해튼 거리 1인 스틸
- 60 ply 이후 합법 수 없음

### 상태 전이

`applyMove()`는 입력 상태를 변경하지 않고 새로운 상태를 반환한다.

- 기물 이동
- 공 소유자 이동 시 공 동행
- 루즈볼 획득
- 동료 패스 또는 루즈볼 패스
- 첫 경로 기물의 슛 선방
- 빈 경로 슛의 득점
- 스틸 및 한 수 보호
- 턴 증가와 득점 후 킥오프

### Lv.1 평가

`src/engine/eval/lv1.ts`가 다음 항목을 조합해 한 국면을 평가한다.

- 득점 차 × 10,000
- 공 소유 기본 보너스
- 공 소유자의 전진도
- 열린 슛 경로
- 인접 스틸 위협
- 루즈볼 접근 거리
- MF와 FW의 위치 보너스

### 최선 수 탐색

`src/engine/search.ts`가 네가맥스와 알파베타 가지치기로 최선 수를 찾는다.

- 호출자가 탐색 깊이와 평가 함수를 전달
- 득점 슛, 선방 슛, 스틸, 패스, 이동 순서로 후보 정렬
- 같은 입력에 같은 최선 수와 루트 후보 점수 반환
- 모든 루트 후보의 `move`와 `score` 반환
- 탐색 노드 수, 깊이, 소요 시간 반환

### Worker 메시지 어댑터

`src/worker/`에는 다음 요청과 응답 타입 및 처리기가 있다.

- `analyze`: 상태와 깊이를 받아 탐색 결과 반환
- `legalMoves`: 상태를 받아 합법 수 반환
- 처리 중 예외는 `error` 응답으로 변환

### 콘텐츠 검증

`tools/validate.ts`가 다음을 검사한다.

- 테마 색상 형식
- 필수 문자열 섹션과 빈 문자열
- 기물 역할별 설정
- 최대 턴 설정
- 퍼즐 ID와 목표 턴
- 퍼즐 기물의 팀, 역할, 보드 범위, 중복 좌표
- 퍼즐 공 소유자 또는 루즈볼 설정

## 부분 구현된 기능

### 브라우저 렌더링

`src/client/main.ts`는 다음을 수행한다.

- `index.html`의 Canvas 획득
- 초기 `GameState` 생성
- 잔디 배경과 보드 격자 렌더링
- home/away 기물과 역할 글자 렌더링
- 루즈볼 렌더링
- `strings.json`의 앱 제목 적용

현재는 `render()`를 한 번만 호출하는 정적 화면이다. 함수 안에서 매번 초기 상태를 생성하므로 게임 상태를 이어갈 수 없다.

### Worker

Worker 파일과 프로토콜은 준비돼 있지만 클라이언트는 아직 Worker를 생성하거나 메시지를 보내지 않는다.

### 콘텐츠 데이터

`theme.json`과 `strings.json`의 앱 제목은 클라이언트에서 사용한다. `pieces.json`과 퍼즐 데이터는 검증되지만 실제 게임 엔진이나 화면 흐름에는 아직 연결되지 않았다.

## 미구현 기능

- Canvas 클릭을 보드 좌표로 변환하는 입력 처리
- 현재 선택된 기물 상태
- 선택 기물의 합법 수 강조
- 사용자가 선택한 수 적용
- 게임 상태 유지 및 턴 진행
- 공 소유 상태 렌더링
- 점수, 현재 팀, 남은 ply UI
- 득점·선방·스틸 피드백
- Worker 생성과 분석 요청
- 봇의 최선 수 적용
- 최선/좋은 수/부정확/실수/블런더 판정
- 경기 종료와 승자 판정 UI
- 퍼즐 JSON을 `GameState`로 변환하는 로더

- 셀프플레이 경기 실행과 통계 집계
- `pieces.json` 설정을 실제 엔진 규칙에 주입하는 연결

## 알려진 간극과 주의점

### 초기 공이 화면에 보이지 않음

초기 상태의 공은 home MF가 소유한다. 현재 `main.ts`는 `ball.kind === "loose"`인 경우만 공을 그리므로 초기 화면에서 공이 보이지 않는다.

### 클라이언트 상태가 지속되지 않음

`render()` 안에서 `createInitialState()`를 호출한다. `render()`를 다시 호출하면 진행 중 상태가 아니라 새로운 초기 상태가 생성된다.

### 기물 설정이 엔진에 주입되지 않음

`content/pieces.json`은 기물 이동 규칙과 최대 턴을 정의하지만 현재 `rules.ts`에도 같은 값이 하드코딩돼 있다. 지금 `pieces.json`을 변경해도 엔진 동작은 변하지 않는다.

### Worker가 클라이언트와 연결되지 않음

`protocol.ts`와 `engine.worker.ts`는 존재하지만 `main.ts`에 Worker 생성 및 요청 코드가 없다.

### 퍼즐 검증은 구조 검사만 수행

퍼즐의 좌표와 필수 필드는 검증하지만 실제로 `goalInTurns` 안에 득점할 수 있는지는 검사하지 않는다.

### 셀프플레이는 자리만 존재

`npm run selfplay`는 아직 구현 전 안내를 출력하고 실패 코드로 종료한다.

### 일부 주석이 현재 TASK 범위와 맞지 않음

`main.ts` 상단 주석은 입력·대국 루프가 S1 범위인 것처럼 설명하지만 실제 S1 TASK는 엔진 이식이었다. 이후 클라이언트 작업 전에 주석을 현재 책임에 맞게 수정해야 한다.

## 다음 작업 전 이해할 기준선

새 기능을 추가하기 전에 다음 흐름을 자신의 말로 설명할 수 있으면 현재 골격을 이해한 것으로 본다.

```text
index.html이 main.ts를 실행한다.
main.ts가 GameState를 받아 Canvas에 그린다.
legalMoves(state)는 가능한 수를 만든다.
applyMove(state, move)는 새로운 상태를 반환한다.
search(state)는 여러 수를 읽고 최선 수와 후보 점수를 반환한다.
Worker는 이 탐색을 브라우저 UI 밖에서 실행하기 위한 어댑터다.
```

## 추천 진행 순서

1. `index.html`과 `src/client/main.ts`의 실행 흐름 이해
2. `src/engine/types.ts`의 `GameState`, `BallState`, `Move` 이해
3. `createInitialState()`와 `applyMove()` 이해
4. `legalMoves()`의 역할별 수 생성 이해
5. 테스트로 각 상태 전이 확인
6. 평가와 탐색은 입력·출력부터 이해한 뒤 재귀 내부로 이동
7. 현재 구조를 이해한 다음 클라이언트 대국 루프 설계

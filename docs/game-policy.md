## 1. 정책 상태와 문서 사용법

### 1.1 상태 표기

| 상태 | 의미 | 변경 조건 |
|---|---|---|
| **[확정]** | 게임 정체성 또는 현재 제품 규칙으로 합의됐고 코드·테스트가 이를 보호한다 | 사용자 승인과 영향 테스트가 필요하다 |
| **[승인]** | 목표 동작으로 합의됐지만 아직 코드·테스트에는 반영되지 않았다 | 구현과 검증을 마치면 [확정]으로 승격한다 |
| **[실험 중]** | 현재 코드에 적용됐지만 밸런스·사용자 경험 검증이 충분하지 않은 값이다 | 측정 결과에 따라 조정할 수 있다 |
| **[제안]** | 앞으로 적용할 후보이며 현재 런타임 동작이 아니다 | 구현·검증 전에는 실제 규칙처럼 설명하지 않는다 |

정책 상태와 구현 상태는 서로 다르다. 예를 들어 “승률 변환식”은 정책상 **[실험 중]**이지만 아직 클라이언트 UI가 없어 구현 상태는 **미구현**이다.

### 1.2 사실의 우선순위

현재 게임이 실제로 어떻게 동작하는지 판단할 때는 다음 순서를 사용한다.

1. 실행되는 `src/engine/` 코드
2. 자동 테스트가 검증하는 동작
3. 이 정책 문서에 기록된 의도
4. `content/*.json`에 선언된 값
5. `reference/prototype.html`의 참조 동작

이 우선순위는 코드가 언제나 옳다는 뜻이 아니다. 코드와 정책이 다르면 **현재 런타임의 사실은 코드**, **수정해야 할 목표는 승인된 정책**으로 구분한다. 불일치를 발견하면 어느 한쪽을 조용히 덮어쓰지 않고 변경 기록에 남긴다.

### 1.3 갱신 규칙

- 규칙이나 수치를 바꾸기 전에 이 문서의 상태, 의도, 예상 영향을 먼저 갱신한다.
- 숫자 변경에는 변경 전 값, 변경 후 값, 이유, 검증 명령, 측정 결과를 남긴다.
- 게임 규칙 변경은 관련 경계값 테스트를 함께 수정하거나 추가한다.
- 평가 가중치 변경은 최소한 결정론 테스트와 셀프플레이 기준 측정을 거친다.
- 구현되지 않은 값은 **[제안]**으로 표시하고 현재 동작처럼 서술하지 않는다.
- `content/pieces.json`과 엔진 하드코딩 값이 모두 존재할 때 실제 연결 여부를 명시한다.
- 매 변경 후 `npm run check`를 통과해야 정책 적용 완료로 기록한다.

### 1.4 핵심 경기 개편 `[승인] 구현 완료·브라우저 검증 전`

2026-08-19 반복 플레이에서 조작 의도와 결과가 직관적으로 연결되지 않고 사건 밀도가 낮다는 문제가 확인됐다. 다음 정책은 사용자 승인을 거쳐 코드와 자동 테스트에 반영됐다.

- 팀 구성을 GK 1, DF 2, MF 2, FW 1의 6대6로 늘린다.
- 필드 선수는 공통 8방향 한 칸 이동을 사용하고, GK는 같은 이동을 자기 골키퍼 박스 안에서만 사용한다.
- 패스는 6칸 이내의 아군을 직접 선택하고, 슛은 골문 행 3·4·5 중 하나를 직접 선택한다.
- 패스와 슛은 같은 정확한 선분 경로 계산을 사용한다. 패스는 첫 접촉 기물이 받고, 슛은 아군을 통과해 첫 상대 기물이 차단한다.
- 막힌 패스와 슛도 선택할 수 있고, 실행 전 성공 경로와 차단 경로를 색상·선 모양·기호로 함께 구분한다.
- 스틸은 8방향으로 인접한 상대 공 소유자를 직접 클릭하며 결정론적으로 성공한다. 후보가 여러 명이면 사용할 아군을 한 번 더 선택한다.
- 팀 턴당 3행동, 3골 선취, 전체 경기 60 원자 행동, 깊이 3 봇, 5초 제한을 사용한다.

세부 좌표, 공개 타입, 미리보기 계약, UI 피드백과 완료 기준은 [핵심 경기 규칙 개편 설계](./superpowers/specs/2026-08-19-core-gameplay-redesign-design.md)가 기준이다. 아래 3장 이후는 현재 M2.6A 런타임의 사실을 설명한다. `npm run check`에서 146개 테스트와 초기·압박 depth-3 성능 기준을 통과했으며, 실제 브라우저 세 경기와 사용자 체감 판단은 아직 남아 있다.

### 1.5 FT&G 벤치마킹 경기 코어 개편 `[승인] 구현·자동 테스트 검증 완료, 실제 플레이 검증 전`

2026-08-22 팀 논의에서 KickMate를 단발성 있는 짧은 게임으로 두고, 엔진 평가와 장기
전략보다 당장 발생하는 공수 선택을 우선하기로 했다. M2.6A의 팀 턴당 3행동,
선수당 최대 2행동, 인접 압박과 버티기, 필드 슛 차단 리바운드는 현재 구현과 자동
테스트에 반영됐다.

확률 판정과 Pass·Shoot·Control·Defense 스탯은 방향만 승인했다. M2.6A 플레이 결과
없이 수치와 포인트 배분을 확정하지 않는다. 상세 경계와 검증 기준은
[FT&G 벤치마킹 경기 코어 개편 설계](./superpowers/specs/2026-08-22-ftg-inspired-match-core-design.md)를
따른다. `npm run check`는 2026-08-22에 153개 테스트를 통과했다. 실제 브라우저 자동
입력 10경기는 수행했지만 사용자 직접 세 경기와 모바일 플레이는 아직 수행하지 않았다.
승인된 비sandbox 실행의 Vite 빌드는 13개 모듈을 157ms에 빌드하며 통과했다.

2026-08-22 플레이 피드백으로 팀 턴 전체에 걸친 재스틸 보호가 회수를 지나치게 막고,
패스 차단·리바운드 소유에는 같은 보호가 없어 소유권 변경이 일관되지 않다는 문제가
확인됐다. 수정 정책은 **모든 직접 소유권 획득에 공을 잃은 팀의 다음 행동 하나만
보호하고, 상대 두 명 이상이 인접한 포위 상태에서는 즉시 보호를 무시**하는 것이다.
이 정책은 엔진·평가·클라이언트 표시와 자동 테스트에 반영됐다. 보호를 만든 바로 그 행동은 유예를 소비하지 않고, 공을 잃은 팀이 다음 원자 행동을 마친 뒤 해제한다.

### 1.6 M2.6B 확률 판정 코어 `[실험 중] 구현·자동 테스트 검증 완료, 사용자 플레이 검증 전`

2026-08-22 사용자 플레이에서 세 문제가 보고됐다. 슛 각이 거의 나오지 않고 막힌 슛은
언제나 무의미하며, 봇에게 공을 잃으면 회수 수단이 없고, 슛 경로 근처의 수비 배치가
아무 효과가 없다. 자동 10경기의 "차단 슛 0%·열린 슛 100%" 단절과 함께, 원인은 모든
패스·슛 판정이 정확한 선분 기하의 100/0 결정론이라는 데 있다고 진단했다.

이에 따라 M2.6B의 확률 판정을 다음 범위로 구현했다. 세부 수치와 경계는
[M2.6B 확률 판정 코어 설계](./superpowers/specs/2026-08-22-m26b-probability-core-design.md)를 따른다.

- 슛 경로 위의 상대 필드 선수는 65%, 상대 GK는 75% 확률로 개입한다. 모든 개입을
  통과하면 득점이므로 막힌 슛도 기대값을 가진 도박이 된다.
- 공 경로에 8방향으로 인접한 상대 기물은 패스·슛 공통으로 20% 확률의 영향권 개입을
  한 번 시도한다. 정확한 선분 위 칸이 아니어도 경로 근처의 수비 배치가 보상받는다.
- 스틸은 사람의 유일한 회수 수단이므로 100% 결정론을 유지한다.
- 판정은 `Math.random()`이 아니라 상태·수 FNV 해시 시드로 결과를 고른다. 같은 국면의
  같은 수는 언제나 같은 결과를 재현한다(정책 2.2 유지).
- 탐색은 실제 판정 결과를 미리 보지 않도록 결과 분포의 기대값(expectiminimax)으로
  수를 평가한다.
- 클라이언트는 패스 도착 확률과 슛 득점 확률을 미리보기에 %로 표시하고, 사람 턴에는
  상대 공 소유자의 현재 슛 위협 레인과 확률을 함께 표시한다.

`npm run check`는 2026-08-22에 156개 테스트로 통과했다. 확률 상수 65/75/20은 모두
**[실험 중]**이며 사용자 직접 플레이 결과로 조정한다.

## 2. 게임 철학

### 2.1 핵심 정체성

| 정책 | 상태 | 의미 |
|---|---|---|
| 교대 턴제 축구 | **[확정]** | 실시간 조작보다 한 수의 선택과 결과를 읽는 전략 게임이다 |
| 재현 가능한 판정 | **[승인]** | M2.6A는 결정론을 유지하고, 후속 확률 버전도 상태 기반 시드로 같은 경기와 분석을 재현한다 |
| 설명 가능한 엔진 | **[확정]** | 최선 수뿐 아니라 모든 루트 후보 점수를 보존해 판정 근거를 만든다 |
| 하나의 순수 엔진 | **[확정]** | 브라우저 대국, 분석, 퍼즐 검산, 셀프플레이가 같은 규칙을 사용한다 |
| 짧은 위험 관리형 전술 축구 | **[승인]** | 5~8분 안에 압박·탈취·슛·리바운드가 이어지는 한 판의 재미를 우선한다 |
| 축구의 chess.com | **[제안]** | 경기 후 리뷰는 핵심 재미가 검증된 뒤 붙이는 차별화 후보다 |
| 데이터 기반 밸런스 | **[제안]** | 향후 셀프플레이와 사용자 테스트로 현재 임의 가중치를 조정한다 |

### 2.2 실행 시점 무작위를 사용하지 않는 이유

- 동일 국면의 최선 수와 블런더 판정을 재현할 수 있다.
- 버그를 같은 상태로 다시 실행해 조사할 수 있다.
- 퍼즐의 해결 가능성과 정답을 안정적으로 검증할 수 있다.
- 밸런스 변경 전후를 같은 조건에서 비교할 수 있다.
- 사용자가 결과를 운보다 선택의 결과로 이해할 수 있다.

금지 대상은 `Math.random()`, 실행 시각에 따른 수 선택, 불안정한 컬렉션 순회에 기대는 동점 처리다. 측정용 시간 `ms`는 기록할 수 있지만 게임 결정에는 사용하지 않는다.

M2.6B의 확률 판정은 이 원칙과 양립한다. 판정 롤은 상태의 게임 결정 요소와 Move를
FNV-1a로 해시한 값이므로 같은 국면의 같은 수는 언제나 같은 결과를 낸다. 플레이어는
결과를 미리 알 수 없어 확률로 체감하지만, 기보만 있으면 모든 판정을 그대로 재실행할
수 있다. 탐색은 해시 결과가 아니라 결과 분포의 기대값을 사용하므로 봇이 판정 결과를
미리 아는 부정도 발생하지 않는다.

## 3. 경기의 기본 구조

### 3.1 보드와 좌표

| 항목 | 현재 값 | 상태 | 코드 |

| 보드 높이 | 9칸, `y = 0..8` | **[확정]** | `BOARD_H` |

골라인 밖 좌표는 슛 궤적의 끝을 계산할 때만 사용한다. 기물과 루즈볼의 정상 위치는 항상 보드 안이어야 한다.

### 3.2 팀과 기물

양 팀은 GK 1명, DF 2명, MF 2명, FW 1명을 가진다. 총 기물 수는 12개다.

| 팀 | 역할 | 기본 위치 | 킥오프 시 변화 |
|---|---|---|---|
| home | GK | `(0, 4)` | 없음 |
| home | DF | `(2, 2)`, `(2, 6)` | 없음 |
| home | MF | `(4, 2)`, `(4, 6)` | 첫 MF가 home 킥오프면 `(6, 4)`로 이동해 공 소유 |
| home | FW | `(5, 4)` | 없음 |
| away | GK | `(12, 4)` | 없음 |
| away | DF | `(10, 6)`, `(10, 2)` | 없음 |
| away | MF | `(8, 6)`, `(8, 2)` | 첫 MF가 away 킥오프면 `(6, 4)`로 이동해 공 소유 |
| away | FW | `(7, 4)` | 없음 |

away의 기본 위치는 home 기본 위치를 `x → 12-x`, `y → 8-y`로 미러링해 계산한다.

### 3.3 턴과 종료

| 정책 | 현재 값 | 상태 | 설명 |
|---|---:|---|---|
| 팀 턴의 행동 수 | 3개 | **[실험 중]** | `move`, `pass`, `shoot`, `steal`, `hold`가 각각 1 행동을 소비한다 |
| 선공 | home | **[확정]** | `turn = 0`에서 시작한다 |
| 차례 계산 | `activeTeam` | **[확정]** | 원자 행동 뒤 남은 행동이 있으면 같은 팀이 계속 행동한다 |
| 선수별 행동 상한 | 팀 턴당 2개 | **[확정]** | `actionCountByPiece`가 상한을 기록한다. `hold`는 팀 행동만 소비하고 이 상한에는 세지 않아 `hold → move` 뒤 패스·슛 선택을 막지 않는다 |
| 조기 종료 | 1행동 뒤 가능 | **[확정]** | `endTurn`은 남은 행동을 버리며 `turn`을 증가시키지 않는다 |
| 경기 길이 | 60 원자 행동 | **[확정]** | `endTurn`을 제외한 행동이 `turn`을 1 증가시킨다 |
| 조기 승리 | 3골 선취 | **[확정]** | 어느 팀이든 3골에 도달한 수 직후 즉시 종료한다 |
| 60 ply 결과 | 종료 시 다득점 | **[확정]** | 점수가 같으면 무승부다 |

현재 `gameResult()`는 3골 선취와 60 ply 결과를 모두 계산한다. 두 종료 상태에서
`legalMoves()`는 빈 배열을, `search()`는 `best: null`을 반환한다. Controller도 사람과
봇의 수 직후 결과를 확인해 즉시 입력을 잠근다. 득점은 `turn`을 초기화하지 않으므로
60 ply는 골 사이 구간이 아니라 경기 전체에 적용된다.

## 4. 상태 모델

### 4.1 `GameState`

```ts
interface GameState {
  turn: number;
  maxTurns: number;
  activeTeam: Team;
  actionsRemaining: number;
  actionCountByPiece: Record<number, number>;
  heldFirmPieceId: number | null;
  pieces: Piece[];
  ball: BallState;
  stealProtection: StealProtection | null;
  score: { home: number; away: number };
}
```

| 필드 | 원리 | 불변 조건 |
|---|---|---|
| `turn` | 적용된 전체 원자 행동 수 | 0 이상이며 `endTurn` 외의 행동마다 1 증가한다 |
| `maxTurns` | 경기 종료 시점 | 현재 기본값은 60이다 |
| `activeTeam` | 현재 팀 턴을 수행하는 팀 | `sideToMove()`가 이 필드를 반환한다 |
| `actionsRemaining` | 현재 팀의 남은 행동 | 3에서 시작해 원자 행동마다 1 감소하며 0에서 팀을 교대한다 |
| `actionCountByPiece` | 현재 팀 턴의 기물별 사용 횟수 | 어떤 기물도 2를 넘지 않는다 |
| `heldFirmPieceId` | 버티기 뒤 이동 허가 대상 | 다음 해당 기물의 이동, 소유권 변경, 득점, 팀 턴 종료 때 해제한다 |
| `pieces` | 기물의 팀·역할·좌표 | ID는 고유하고 좌표는 보드 안이며 서로 겹치지 않는다 |
| `ball` | 소유 중 또는 루즈볼 중 하나 | held면 존재하는 기물 ID, loose면 보드 좌표를 가진다 |
| `stealProtection` | 즉시 재스틸 보호 | 보호 소유자·차단 팀·남은 차단 행동 1회를 명시하며, 2인 포위에서는 무시한다 |
| `score` | 양 팀의 누적 득점 | 0 이상의 정수다 |

### 4.2 공 상태

```text
held(pieceId)
  공의 위치 = 해당 기물의 위치

loose(x, y)
  소유자 없음
  기물이 해당 칸으로 이동하면 즉시 held로 전환
```

공 소유와 별도 공 좌표를 동시에 저장하지 않는다. 이 구조는 “기물이 공을 들고 있는데 공 좌표가 다른 칸을 가리키는” 모순을 타입 단계에서 막는다.

### 4.3 상태 전이의 순수성

**[확정]** `applyMove(state, move)`는 입력 상태를 변경하지 않고 내부 객체까지 복제한 새 상태를 반환한다.

이 원칙은 다음 이유로 필수다.

- 탐색기가 같은 부모 상태에서 여러 후보를 안전하게 비교한다.
- 분석 화면이 수를 두기 전 국면을 보존할 수 있다.
- 경기 후 리뷰가 과거 상태를 그대로 재현할 수 있다.
- 테스트에서 입력 변경 여부를 명확하게 검증할 수 있다.

현재 `applyMove()`는 호출자가 `legalMoves()`에서 얻은 합법 수를 전달한다고 가정한다. 존재하지 않는 기물이나 불법 목적지를 다시 검증하지 않는다. 외부 입력을 직접 `applyMove()`에 넣는 코드는 정책 위반이다.

## 5. 합법 수 정책

### 5.1 공통 이동 규칙

- 현재 차례 팀의 모든 기물은 공 소유 여부와 관계없이 일반 이동을 할 수 있다.
- 정상 이동 목적지는 보드 안의 빈 칸이어야 한다.
- 모든 필드 선수는 역할과 관계없이 상하좌우·대각선의 인접한 한 칸으로 이동한다.
- 공 소유 기물이 움직이면 공도 함께 이동한 것으로 처리한다.
- 기물이 루즈볼 칸으로 이동하면 즉시 공을 소유한다.

있다. 개입 관문은 경로 진행 순서대로 평가하며 한 기물은 한 번의 슛에서 최대 한 번만
시도한다. 모든 관문을 통과하면 득점이므로, 예를 들어 필드 선수 한 명 뒤 GK가 있는
슛은 0.35×0.25 ≈ 9% 확률로 들어간다. 미리보기는 대표 차단자(가장 먼저 개입 가능한
상대), 예상 리바운드 칸, 득점 확률을 상태 전이 전에 제공한다. 리바운드 후보는 차단자
인접 빈 칸을 슈터와의 거리 제곱, `y`, `x` 순으로 정렬해 고르므로 같은 상태에서 언제나
같은 칸을 선택한다.

### 5.5 득점과 킥오프

득점 시 상태 전이는 다음 순서를 따른다.

```text
득점 팀 점수 +1
  → turn +1
  → 모든 기물을 기본 위치로 복원
  → 실점 팀 MF를 센터 (6,4)로 이동
  → 실점 팀 MF가 공 소유
  → stealProtection = null
  → 실점 팀의 3행동 팀 턴
  → 실점 팀 차례로 경기 재개
```

**[확정]** 득점한 팀이 아니라 실점한 팀이 다음 킥오프를 수행한다.

### 5.6 스틸과 1행동 회수 유예

| 항목 | 현재 정책 | 상태 |
|---|---|---|
| 대상 | 상대 팀의 공 소유자 | **[확정]** |
| 거리 | 체비쇼프 거리 1, 상하좌우·대각선 인접 | **[확정]** |
| 성공 확률 | 100%, 무작위 없음 | **[확정]** |
| 실행 조건 | 보호되지 않았거나 상대 두 명 이상이 인접해 포위됨 | **[확정]** |
| 성공 후 보호 | 새 소유자는 공을 잃은 팀의 다음 행동 하나 동안 보호 | **[확정]** |
| 다른 획득 후 보호 | 패스 차단·선방·필드 소유·루즈볼 획득에도 같은 보호 적용 | **[확정]** |
| 포위 예외 | 보호 소유자에게 상대 두 명 이상이 인접하면 즉시 스틸 허용 | **[확정]** |

이 수정안은 2026-08-22에 구현되어 자동 테스트가 보호한다. `stealProtection`은 보호받는 기물, 스틸이 금지된 팀, 남은 보호
행동 수 1을 기록한다. 차단 팀이 원자 행동 하나를 완료하거나 `endTurn`을 실행하면
해제된다. 단, 보호 소유자에게 차단 팀 기물 두 명 이상이 8방향으로 인접하면 남은 보호
행동 수와 관계없이 즉시 스틸할 수 있다. 같은 팀의 일반 패스와 득점 뒤 킥오프는 새
보호를 만들지 않으며, 공이 소유자를 떠나면 기존 보호를 해제한다.

사용자는 상대 공 소유자를 직접 클릭해 스틸한다. 가능한 내 기물이 하나면 즉시 적용하고,
둘 이상이면 사용할 스틸러 후보를 한 번 더 선택한다. 보호 중인 공 소유자에는 `◆`를 표시한다.

## 6. 상태 전이 요약

| Move | 기물 변화 | 공 변화 | 보호 변화 | 점수·팀 턴 |
|---|---|---|---|---|
| `move` | 실행 기물이 빈 칸으로 이동 | 소유자가 움직이면 held 유지, 루즈볼 칸이면 소유 | 루즈볼 회수 시 상대의 다음 행동 1회를 차단 | 원자 행동 +1 |
| `pass` 도착 | 없음 | 경로에서 처음 만난 기물이 held | 상대가 차단해 소유하면 패스 팀의 다음 행동 1회를 차단 | 원자 행동 +1 |
| `pass` 영향권 인터셉트 | 없음 | 경로 인접 상대가 held | 패스 팀의 다음 행동 1회를 차단 | 원자 행동 +1 |
| `shoot` GK 선방 | 없음 | GK가 held | 슈팅 팀의 다음 행동 1회를 차단 | 원자 행동 +1 |
| `shoot` 필드 차단 | 없음 | 루즈볼 또는 차단자가 held | 차단자가 직접 소유하면 슈팅 팀의 다음 행동 1회를 차단 | 원자 행동 +1 |
| `shoot` 득점 | 전체 기본 배치 복원 | 실점 팀 MF가 held | 해제 | 점수 +1, 원자 행동 +1, 실점 팀 3행동 |
| `steal` | 없음 | 실행 기물이 held | 상대의 다음 행동 1회를 차단 | 원자 행동 +1 |
| `hold` | 없음 | held 유지 | 기존 보호의 차단 팀이 실행하면 행동 뒤 해제 | 원자 행동 +1, 선수별 사용 횟수 증가 없이 다음 이동 한 번 허용 |
| `endTurn` | 없음 | 변화 없음 | 차단 팀이 실행하면 해제 | 원자 행동 증가 없이 팀 교대 |

같은 상태와 같은 Move는 같은 새 상태를 만들어야 한다. 확률 관문이 있는 패스·슛은
`applyMoveOutcomes()`가 가능한 결과와 확률을 열거하고, `applyMove()`가 상태·수 해시
롤로 그중 하나를 결정적으로 선택한다. 렌더링, 애니메이션, Worker 통신은 이 표의
결과를 바꾸지 않는다.

## 7. 탐색 정책

### 7.1 고정 루트 관점 minimax

**[확정]** 팀 턴 안에서 같은 팀이 연속 행동하므로 루트 팀 관점을 고정한 minimax로 탐색한다.

```text
루트 팀 행동 노드 = 자식 점수의 최댓값
상대 팀 행동 노드 = 자식 점수의 최솟값
```

말단 상태에서는 `evalLv1(state, 루트 팀)`으로 평가한다. 같은 팀의 연속 행동에서는 계속
최댓값을 선택하고, `activeTeam`이 상대 팀으로 바뀐 노드에서만 최솟값을 선택한다.

확률 관문이 있는 수는 하나의 결과가 아니라 `applyMoveOutcomes()`가 열거한 결과
분포의 확률 가중 합(기대값)으로 평가한다(expectiminimax). 탐색이 해시 롤의 실제
결과를 미리 사용하면 봇이 판정을 아는 부정이 되므로 금지한다. 결과가 하나뿐인
결정론적 수는 기존 알파베타 창을 그대로 사용하고, 확률 분기가 있는 수의 각 분기는
전체 창으로 평가한다.

### 7.2 알파베타 가지치기

- `alpha`: 루트 팀이 이미 보장한 최저 점수
- `beta`: 상대가 허용할 최고 경계
- `alpha >= beta`가 되면 남은 후보는 상위 선택을 바꾸지 못하므로 생략한다.

가지치기는 최종 판단 규칙을 바꾸지 않고 불필요한 탐색만 줄여야 한다. 같은 깊이의 완전한 minimax와 동일한 최선 점수를 반환하는 것이 원칙이다.

### 7.3 탐색 깊이

| 항목 | 현재 상태 | 정책 상태 |
|---|---|---|
| 깊이 전달 방식 | 호출자가 `SearchOptions.depth`로 지정 | **[확정]** |
| 브라우저 기본 깊이 | 깊이 3 | **[확정]** |
| 셀프플레이 깊이 | 하네스 미구현 | **[제안]** 명령행 인자 |

깊이가 높을수록 더 먼 수를 보지만 노드 수와 대기 시간이 커진다. S2 Controller는
모든 봇 분석에 깊이 3을 전달하며 테스트가 이를 보호한다. 이후 장치별 응답 시간과
수 품질 측정에 따라 변경을 제안할 수 있지만 현재 브라우저 기본값은 3으로 확정한다.

### 7.4 수 정렬 우선순위

| 수 종류 | 정렬 점수 | 상태 | 의미 |
|---|---:|---|---|
| 확률 1 열린 슛 | 100 | **[실험 중]** | 개입 없이 확실히 득점하는 강제 수를 먼저 탐색 |
| 개입이 남은 슛 | 60 | **[실험 중]** | 확률 관문을 뚫어야 하는 슛을 다음으로 탐색 |
| 스틸 | 50 | **[실험 중]** | 즉시 소유권을 바꾸는 수 |
| 패스 | 30 | **[실험 중]** | 공 위치와 소유를 바꾸는 수 |
| 버티기 | 20 | **[실험 중]** | 압박 속 다음 이동을 준비하는 수 |
| 일반 이동 | 0 | **[실험 중]** | 나머지 위치 변화 |
| 턴 종료 | -10 | **[실험 중]** | 남은 행동을 포기하는 수 |

이 점수는 국면 평가 가중치가 아니다. **탐색 순서만 정하고 최선 수는 재귀 평가 결과로 결정한다.** 따라서 100점 열린 슛이 항상 50점 스틸보다 좋은 수라는 뜻이 아니다.

같은 정렬 점수에서는 `legalMoves()`가 생성한 원래 순서를 유지한다. 평가 점수까지 같으면 먼저 정렬된 수가 `best`로 남아 동점을 결정론적으로 처리한다.

### 7.5 탐색 결과

```ts
interface SearchResult {
  best: Move | null;
  score: number;
  values: Array<{ move: Move; score: number }>;
  nodes: number;
  depth: number;
  ms: number;
}
```

- `best`: 현재 탐색에서 가장 높은 점수의 수
- `score`: 루트 현재 팀 관점의 최선 점수
- `values`: 모든 루트 후보와 점수. 블런더 판정의 근거다.
- `nodes`: 재귀에서 방문한 하위 상태 수
- `depth`: 요청한 탐색 깊이
- `ms`: 측정된 실행 시간. 게임 결정에는 사용하지 않는다.

## 8. Lv.1 평가 정책

### 8.1 평가 공식

현재 평가는 특정 `perspective` 팀 관점의 숫자 하나를 반환한다.

```text
E(state, perspective)
  = 득점 차 가치
  + 공 상태 가치
  + 전체 기물 위치 가치
```

양수는 관점 팀에게 유리하고, 음수는 상대에게 유리하다. 대칭 국면에서 관점을 바꾸면 부호가 반전되어야 한다.

### 8.2 전체 가중치 표

| ID | 평가 항목 | 현재 값 | 적용 방식 | 상태 |
|---|---|---:|---|---|
| EV-01 | 골 차이 | `10,000 / 골` | `(내 득점 - 상대 득점) × 10,000` | **[실험 중]** |
| EV-02 | 공 소유 기본값 | `140` | 소유 팀에 더하고 상대 관점에는 뺌 | **[실험 중]** |
| EV-03 | 공 소유자 전진도 | `9 / 칸` | 소유자의 공격 방향 진행 칸 × 9 | **[실험 중]** |
| EV-04 | 슛 위협 | `+450 × 최고 득점 확률` | 현재 공 소유자의 가장 유망한 슛 득점 확률(0..1)에 비례 적용 | **[실험 중]** |
| EV-05 | 인접 스틸 위협 | `-170` | 공 소유자 주변 8칸에 상대 기물이 하나라도 있으면 적용 | **[실험 중]** |
| EV-06 | 루즈볼 접근성 | `30 / 거리 차` | 양 팀 최소 체비쇼프 거리 차 × 30 | **[실험 중]** |
| EV-07 | FW 전진 위치 | `3 / 칸` | 모든 FW의 공격 방향 진행 칸 × 3 | **[실험 중]** |
| EV-08 | MF 전진 위치 | `1.5 / 칸` | 모든 MF의 공격 방향 진행 칸 × 1.5 | **[실험 중]** |
| EV-09 | DF·GK 전진 위치 | `0` | 별도 위치 보너스 없음 | **[실험 중]** |

이 값들은 `reference/prototype.html`에서 작동을 검증한 휴리스틱을 이식한 것이다. 현재 코드와 테스트에 존재하지만 셀프플레이와 사용자 경기로 밸런스가 검증되지 않았으므로 모두 **[실험 중]**이다.

### 8.3 공 소유 평가

공이 held라면 다음 식을 사용한다.

```text
소유 가치
  = 140
  + 소유자 전진 칸 × 9
  + 450 × 가장 유망한 슛의 득점 확률(0..1)
  - 인접 상대가 있으면 170
```

소유 팀이 관점 팀이면 이 값을 더하고 상대 팀이면 뺀다.

의도와 위험:

| 항목 | 의도 | 확인해야 할 위험 |
|---|---|---|
| 기본 140 | 루즈볼보다 안정적 소유를 선호 | 의미 없는 소유 유지가 공격보다 과대평가될 수 있음 |
| 전진 9 | 상대 골대 쪽 소유를 선호 | 측면·수비적 재배치 가치가 과소평가될 수 있음 |
| 열린 슛 450 | 즉시 득점 위협을 강하게 선호 | 슛의 실제 장기 가치보다 과도할 수 있음 |
| 위협 -170 | 빼앗길 위험을 반영 | `stealProtection`과 압박의 전략 가치가 균형에 미치는 영향을 실제 플레이로 확인해야 함 |

EV-05는 `stealProtection`으로 현재 팀이 실제 스틸할 수 없는 인접 상대는 위험으로
감점하지 않는다. 보호와 압박을 구분하는 이 동작은 자동 테스트로 보호하지만, 가중치
자체는 여전히 **[실험 중]**이다.

### 8.4 루즈볼 평가

공이 loose라면 각 팀에서 공에 가장 가까운 기물의 체비쇼프 거리를 구한다.

```text
home 관점 루즈볼 가치
  = (away 최소 거리 - home 최소 거리) × 30
```

away 관점에서는 부호를 반전한다.

체비쇼프 거리 `max(|dx|, |dy|)`는 필드 선수의 공통 8방향 한 칸 이동과 일치한다.
다만 GK의 박스 제한, 목적지 점유와 다른 기물 때문에 우회해야 하는 상황은 반영하지
않으므로 모든 국면에서 정확한 도달 턴을 뜻하지는 않는다.

현재 방식은 계산이 빠르고 대칭적이라는 장점이 있다. 정확한 역할별 최단 수 계산으로 교체할지는 셀프플레이 성능과 수 품질을 측정한 뒤 결정한다.

### 8.5 위치 평가

공과 별도로 모든 FW와 MF의 공격 방향 전진도를 평가한다.

```text
기물 위치 가치
  = Σ(팀 부호 × 공격 방향 진행 칸 × 역할 가중치)

FW 가중치 = 3
MF 가중치 = 1.5
DF, GK 가중치 = 0
```

의도는 공격 역할이 전진 공간을 차지하도록 유도하는 것이다. 수비 라인 유지, 중앙 장악, 패스 연결성은 현재 직접 평가하지 않는다.

### 8.6 골 가치의 상대적 크기

한 골은 10,000점이다. 비교를 위해 보드 끝까지 전진한 한 팀의 FW 위치 보너스 최대는 `12 × 3 = 36`, MF는 `12 × 1.5 = 18`이다. 공 소유자가 최대 전진하고 열린 슛을 가지면 기본 소유 항은 대략 `140 + 108 + 450 = 698`이다.

따라서 현재 설계에서는 한 골이 위치·소유상의 일반적인 차이보다 압도적으로 중요하다. 이는 실제 득점을 다른 휴리스틱보다 우선하려는 의도이며, 최소 한 골 우위가 평가 부호를 뒤집지 않는지 테스트로 계속 보호해야 한다.

## 9. 분석 UI 정책

분석 UI는 아직 본편에 구현되지 않았다. 아래 값은 프로토타입에서 검증된 현재 **[실험 중]** 기준이다.

### 9.1 평가값의 승률 표시

```text
추정 승률 = 1 / (1 + exp(-평가값 / 900))
```

| 평가값 | 표시되는 추정 승률 |
|---:|---:|
| `-1,800` | 약 11.9% |
| `-900` | 약 26.9% |
| `0` | 50.0% |
| `+900` | 약 73.1% |
| `+1,800` | 약 88.1% |

분모 900은 곡선의 민감도를 정한다. 이 값은 실제 경기 결과로 통계 보정한 확률이 아니다. UI에서는 검증 전까지 **“승률”보다 “추정 승률”**로 표기해야 한다.

골 가치가 10,000점이라 한 골 차이는 이 공식에서 거의 100% 또는 0%로 포화된다. 경기 중 역전 가능성을 보여주고 싶다면 골 가치, 승률 스케일, 남은 턴을 함께 고려한 별도 보정이 필요하다.

### 9.2 수 품질 판정

사람 차례 시작 시 모든 루트 후보를 분석하고 다음 값을 계산한다.

```text
delta = 최선 수 점수 - 실제로 둔 수 점수
```

| delta 범위 | 판정 | 상태 |
|---:|---|---|
| `< 40` | 최선 | **[실험 중]** |
| `40..149` | 좋은 수 | **[실험 중]** |
| `150..349` | 부정확 | **[실험 중]** |
| `350..699` | 실수 | **[실험 중]** |
| `>= 700` | 블런더 | **[실험 중]** |

경계값은 현재 평가 스케일에 종속된다. 평가 가중치를 바꾸면 같은 수의 delta도 달라질 수 있으므로 EV 가중치와 판정 임계값을 독립적으로 조정하면 안 된다.

검증 기준:

- 골을 놓치는 수가 실수 또는 블런더로 분류되는가?
- 의미가 거의 같은 동점 수가 최선 또는 좋은 수로 남는가?
- 게임 초반의 작은 위치 차이를 과도하게 블런더로 부르지 않는가?
- 탐색 깊이가 달라져도 판정이 지나치게 흔들리지 않는가?

### 9.3 판정 문구

표시 문자열은 `content/strings.json`의 다음 키를 사용한다.

```text
best        최선
good        좋은 수
inaccuracy  부정확
mistake     실수
blunder     블런더!
```

판정 계산은 엔진·분석 정책이고, 문구와 어조는 콘텐츠 정책이다. 문자열 변경이 수치 판정을 바꾸면 안 된다.

## 10. 코드와 content 설정의 관계

### 10.1 현재 불일치

`content/pieces.json`에는 다음 값이 선언돼 있다.

```text
GK range 1
DF range 2
MF range 2
FW knight range 1
passDirections 8
stealProtectionTurns 1
maxTurns 60
```

그러나 현재 `src/engine/rules.ts`는 이 JSON을 읽지 않는다. 역할별 JSON 이동값과 현재
공통 인접 1칸 이동 규칙도 다르므로 JSON을 변경해도 실제 게임 규칙은 바뀌지 않는다.

| 항목 | JSON 선언 | 현재 코드 | 런타임 기준 |
|---|---:|---:|---|
| GK 이동 | 1 | 1 | 코드 |
| DF 이동 | 직선 2칸 | 8방향 인접 1칸 | 코드 |
| MF 이동 | 전방향 2칸 | 8방향 인접 1칸 | 코드 |
| FW 이동 | 나이트 점프 | 8방향 인접 1칸 | 코드 |
| 패스 방향 | 8 | 체비쇼프 거리 6 이내 아군 직접 선택 | 코드 |
| 스틸 보호 | 숫자 1 | 구조화된 다음 행동 1회·2인 포위 예외 | 코드 |
| 최대 턴 | 60 | 60 | 코드 |

GK 이동과 최대 행동 수만 현재 런타임 값과 일치하며, 어떤 항목도 JSON에 연결돼 있지 않다.

### 10.2 목표 정책

**[제안]** 룰 설정을 순수 데이터 객체로 만들어 엔진 함수에 주입하고 `content/pieces.json`은 클라이언트·도구 계층에서 파싱한다.

```text
content/pieces.json
  → 설정 검증
  → RuleConfig 생성
  → createInitialState(config)
  → legalMoves(state, config)
  → applyMove(state, move, config)
```

엔진이 직접 파일을 읽거나 브라우저 import에 의존해서는 안 된다. 기본 설정은 코드에 보존해 테스트와 Node 셀프플레이가 명시적인 설정 없이도 같은 기준으로 실행되게 한다.

설정 주입이 구현되기 전까지는 `content/pieces.json`을 밸런스 조정의 실제 입력으로 설명하지 않는다.

## 11. 불변 조건과 검증 정책

### 11.1 반드시 유지할 불변 조건

- 모든 기물 좌표는 보드 안에 있다.
- 두 기물이 같은 칸을 점유하지 않는다.
- held 공은 존재하는 기물 ID를 가리킨다.
- loose 공은 보드 안 좌표를 가진다.
- 한 수는 현재 차례 팀의 합법 수 목록에서 선택한다.
- `applyMove()`는 입력 상태를 변경하지 않는다.
- 득점 후 실점 팀이 킥오프한다.
- `turn >= maxTurns`에서 합법 수와 최선 수가 없다.
- 동일 상태·깊이·평가 함수는 동일한 논리적 탐색 결과를 낸다.
- 측정 시간 `ms`만 결정론 비교에서 제외한다.

### 11.2 현재 자동 테스트 범위

1. 초기 6대6 배치와 home MF 킥오프
2. 보드 범위와 기물 좌표 중복
3. 초기 합법 수 존재
4. 이동·패스 목적지 범위

## 12. 정책 변경 절차

### 12.1 고정 규칙 변경

1. 변경할 정책과 플레이어 경험상의 이유를 적는다.
2. **[확정]**을 바로 수정하지 않고 변경 후보를 **[제안]**으로 추가한다.
3. 영향을 받는 합법 수, 상태 전이, 평가, UI, content 키를 나열한다.
4. 기존 동작을 보여주는 테스트와 새 기대 동작 테스트를 비교한다.
5. 사용자 승인을 받는다.
6. 코드를 구현하고 `npm run check`를 실행한다.
7. 대표 경기 또는 퍼즐로 사람이 결과를 확인한다.
8. 승인된 후보를 **[확정]**으로 승격하고 변경 기록을 남긴다.

### 12.2 실험 가중치 변경

1. 가설을 한 문장으로 적는다. 예: “열린 슛 보너스 450이 지나치게 커 봇이 무리한 슛 진입을 선호한다.”
2. 변경 전 기준 셀프플레이 결과와 대표 국면 점수를 기록한다.
3. 한 번에 가능한 한 하나의 가중치만 바꾼다.
4. 변경 후 같은 조건을 재실행한다.
5. 승률뿐 아니라 평균 골, 평균 수, 분기 수, 대표 수 선택을 비교한다.
6. 사용자 플레이에서 전략이 더 이해하기 쉬워졌는지 확인한다.
7. 채택 또는 롤백 결정을 실험 기록에 남긴다.

### 12.3 상태 승격 기준

**[실험 중] → [확정]** 승격에는 다음이 필요하다.

- 값의 의도를 한 문장으로 설명할 수 있다.
- 자동 테스트가 관련 불변 조건을 보호한다.
- 셀프플레이 또는 고정 국면 비교 결과가 있다.
- 최소 한 번의 실제 사용자 플레이에서 치명적인 이상 행동이 없다.
- 해당 값과 연결된 UI 설명이 오해를 만들지 않는다.

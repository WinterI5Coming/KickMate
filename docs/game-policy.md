## 1. 정책 상태와 문서 사용법

### 1.1 상태 표기

| 상태 | 의미 | 변경 조건 |
|---|---|---|
| **[확정]** | 게임 정체성 또는 현재 제품 규칙으로 합의됐고 코드·테스트가 이를 보호한다 | 사용자 승인과 영향 테스트가 필요하다 |
| **[실험 중]** | 현재 코드에 적용됐지만 밸런스·사용자 경험 검증이 충분하지 않은 값이다 | 측정 결과에 따라 조정할 수 있다 |
| **[제안]** | 앞으로 적용할 후보이며 현재 런타임 동작이 아니다 | 구현·검증 전에는 실제 규칙처럼 설명하지 않는다 |

정책 상태와 구현 상태는 서로 다르다. 예를 들어 “승률 변환식”은 정책상 **[실험 중]**이지만 아직 클라이언트 UI가 없어 구현 상태는 **미구현**이다.

### 1.2 사실의 우선순위

현재 게임이 실제로 어떻게 동작하는지 판단할 때는 다음 순서를 사용한다.

1. 실행되는 `src/engine/` 코드
2. 자동 테스트가 검증하는 동작
3. 이 정책 문서에 기록된 의도
4. `content/*.json`에 선언된 값
5. `reference/prototype.html`의 참조 동작

이 우선순위는 코드가 언제나 옳다는 뜻이 아니다. 코드와 정책이 다르면 **현재 런타임의 사실은 코드**, **수정해야 할 목표는 승인된 정책**으로 구분한다. 불일치를 발견하면 어느 한쪽을 조용히 덮어쓰지 않고 변경 기록에 남긴다.

### 1.3 갱신 규칙

- 규칙이나 수치를 바꾸기 전에 이 문서의 상태, 의도, 예상 영향을 먼저 갱신한다.
- 숫자 변경에는 변경 전 값, 변경 후 값, 이유, 검증 명령, 측정 결과를 남긴다.
- 게임 규칙 변경은 관련 경계값 테스트를 함께 수정하거나 추가한다.
- 평가 가중치 변경은 최소한 결정론 테스트와 셀프플레이 기준 측정을 거친다.
- 구현되지 않은 값은 **[제안]**으로 표시하고 현재 동작처럼 서술하지 않는다.
- `content/pieces.json`과 엔진 하드코딩 값이 모두 존재할 때 실제 연결 여부를 명시한다.
- 매 변경 후 `npm run check`를 통과해야 정책 적용 완료로 기록한다.

## 2. 게임 철학

### 2.1 핵심 정체성

| 정책 | 상태 | 의미 |
|---|---|---|
| 교대 턴제 축구 | **[확정]** | 실시간 조작보다 한 수의 선택과 결과를 읽는 전략 게임이다 |
| 완전 결정론 | **[확정]** | 슛 성공률, 스틸 성공률, AI 선택에 무작위를 사용하지 않는다 |
| 설명 가능한 엔진 | **[확정]** | 최선 수뿐 아니라 모든 루트 후보 점수를 보존해 판정 근거를 만든다 |
| 하나의 순수 엔진 | **[확정]** | 브라우저 대국, 분석, 퍼즐 검산, 셀프플레이가 같은 규칙을 사용한다 |
| 축구의 chess.com | **[확정]** | 승패보다 “어느 수가 왜 나빴는가”를 보여주는 경기 후 리뷰가 핵심 가치다 |
| 데이터 기반 밸런스 | **[제안]** | 향후 셀프플레이와 사용자 테스트로 현재 임의 가중치를 조정한다 |

### 2.2 무작위를 사용하지 않는 이유

- 동일 국면의 최선 수와 블런더 판정을 재현할 수 있다.
- 버그를 같은 상태로 다시 실행해 조사할 수 있다.
- 퍼즐의 해결 가능성과 정답을 안정적으로 검증할 수 있다.
- 밸런스 변경 전후를 같은 조건에서 비교할 수 있다.
- 사용자가 결과를 운보다 선택의 결과로 이해할 수 있다.

금지 대상은 `Math.random()`, 실행 시각에 따른 수 선택, 불안정한 컬렉션 순회에 기대는 동점 처리다. 측정용 시간 `ms`는 기록할 수 있지만 게임 결정에는 사용하지 않는다.

## 4. 상태 모델

### 4.1 `GameState`

```ts
interface GameState {
  turn: number;
  maxTurns: number;
  pieces: Piece[];
  ball: BallState;
  noSteal: number;
  score: { home: number; away: number };
}
```

| 필드 | 원리 | 불변 조건 |
|---|---|---|
| `turn` | 적용된 전체 ply 수이자 현재 차례의 근거 | 0 이상이며 한 수마다 1 증가한다 |
| `maxTurns` | 경기 종료 시점 | 현재 기본값은 60이다 |
| `pieces` | 기물의 팀·역할·좌표 | ID는 고유하고 좌표는 보드 안이며 서로 겹치지 않는다 |
| `ball` | 소유 중 또는 루즈볼 중 하나 | held면 존재하는 기물 ID, loose면 보드 좌표를 가진다 |
| `noSteal` | 즉시 재스틸 방지 카운터 | 0이면 스틸 가능, 현재 룰에서는 0 또는 1을 사용한다 |
| `score` | 양 팀의 누적 득점 | 0 이상의 정수다 |

### 4.2 공 상태

```text
held(pieceId)
  공의 위치 = 해당 기물의 위치

loose(x, y)
  소유자 없음
  기물이 해당 칸으로 이동하면 즉시 held로 전환
```

공 소유와 별도 공 좌표를 동시에 저장하지 않는다. 이 구조는 “기물이 공을 들고 있는데 공 좌표가 다른 칸을 가리키는” 모순을 타입 단계에서 막는다.

### 4.3 상태 전이의 순수성

**[확정]** `applyMove(state, move)`는 입력 상태를 변경하지 않고 내부 객체까지 복제한 새 상태를 반환한다.

이 원칙은 다음 이유로 필수다.

- 탐색기가 같은 부모 상태에서 여러 후보를 안전하게 비교한다.
- 분석 화면이 수를 두기 전 국면을 보존할 수 있다.
- 경기 후 리뷰가 과거 상태를 그대로 재현할 수 있다.
- 테스트에서 입력 변경 여부를 명확하게 검증할 수 있다.

현재 `applyMove()`는 호출자가 `legalMoves()`에서 얻은 합법 수를 전달한다고 가정한다. 존재하지 않는 기물이나 불법 목적지를 다시 검증하지 않는다. 외부 입력을 직접 `applyMove()`에 넣는 코드는 정책 위반이다.

## 5. 합법 수 정책

### 5.1 공통 이동 규칙

- 현재 차례 팀의 모든 기물은 공 소유 여부와 관계없이 일반 이동을 할 수 있다.
- 정상 이동 목적지는 보드 안의 빈 칸이어야 한다.
- 슬라이드 이동은 기물을 뛰어넘지 못한다.
- 공 소유 기물이 움직이면 공도 함께 이동한 것으로 처리한다.
- 기물이 루즈볼 칸으로 이동하면 즉시 공을 소유한다.

| DF | 상하좌우 최대 2칸 슬라이드 | 첫 기물에서 중단 | 보드 안 | **[확정]** |

현재 선방은 GK만의 능력이 아니다. 슛 경로에서 가장 먼저 만난 **어떤 기물이든**, 심지어 슈터와 같은 팀의 기물도 공을 소유하며 슛을 막는다. 이는 프로토타입에서 이식된 단순화 규칙이다.

검증해야 할 질문:

- 아군 기물에 막힌 슛을 “선방”으로 부르는 것이 자연스러운가?
- GK에게만 별도 선방 규칙을 주면 역할 정체성이 좋아지는가?
- 모든 기물 차단 규칙이 전략적 가독성과 결정론을 단순하게 유지하는 장점이 더 큰가?

이 정책을 바꾸기 전에는 슛 경로 테스트와 평가 함수의 열린 슛 보너스를 함께 검토해야 한다.

### 5.5 득점과 킥오프

득점 시 상태 전이는 다음 순서를 따른다.

```text
득점 팀 점수 +1
  → turn +1
  → 모든 기물을 기본 위치로 복원
  → 실점 팀 MF를 센터 (6,4)로 이동
  → 실점 팀 MF가 공 소유
  → noSteal = 0
  → 실점 팀 차례로 경기 재개
```

**[확정]** 득점한 팀이 아니라 실점한 팀이 다음 킥오프를 수행한다.

### 5.6 스틸과 보호 턴

| 항목 | 현재 정책 | 상태 |

| 대상 | 상대 팀의 공 소유자 | **[확정]** |
| 거리 | 맨해튼 거리 1, 상하좌우 인접 | **[확정]** |
| 성공 확률 | 100%, 무작위 없음 | **[확정]** |

| 성공 후 보호 | `noSteal = 1` | **[확정]** |
| 선방 후 보호 | `noSteal = 1` | **[확정]** |

보호 카운터는 수를 적용할 때 먼저 1 감소한다. 스틸 또는 선방 직후 상대의 다음 차례에는 `noSteal = 1`이므로 스틸 후보가 생성되지 않는다. 그 상대가 다른 행동을 하면 적용 시 0이 되고 이후 다시 스틸할 수 있다.

## 6. 상태 전이 요약

| Move | 기물 변화 | 공 변화 | 보호 변화 | 점수·턴 |
|---|---|---|---|---|
| `move` | 실행 기물이 빈 칸으로 이동 | 소유자가 움직이면 held 유지, 루즈볼 칸이면 소유 | 기존 카운터 1 감소 | 턴 +1 |
| `pass` | 없음 | 아군 목적지면 held, 빈 목적지면 loose | 기존 카운터 1 감소 | 턴 +1 |
| `shoot` 선방 | 없음 | 경로 첫 기물이 held | 1 | 턴 +1 |
| `shoot` 득점 | 전체 기본 배치 복원 | 실점 팀 MF가 held | 0 | 점수 +1, 턴 +1 |
| `steal` | 없음 | 실행 기물이 held | 1 | 턴 +1 |

같은 상태와 같은 Move는 같은 새 상태를 만들어야 한다. 렌더링, 애니메이션, Worker 통신은 이 표의 결과를 바꾸지 않는다.

## 7. 탐색 정책

### 7.1 네가맥스 원리

**[확정]** 두 팀이 번갈아 행동하는 제로섬 구조를 네가맥스로 탐색한다.

```text
현재 팀의 점수 = -(상대 차례에서 상대가 얻을 수 있는 최선 점수)
```

말단 상태에서는 `evalLv1(state, 현재 차례 팀)`으로 평가한다. 재귀가 한 단계 돌아올 때 점수 부호를 뒤집어 루트 팀 관점으로 통일한다.

### 7.2 알파베타 가지치기

- `alpha`: 현재 팀이 이미 보장한 최저 점수
- `beta`: 상대가 허용할 최고 경계
- `alpha >= beta`가 되면 남은 후보는 상위 선택을 바꾸지 못하므로 생략한다.

가지치기는 최종 판단 규칙을 바꾸지 않고 불필요한 탐색만 줄여야 한다. 같은 깊이의 완전한 네가맥스와 동일한 최선 점수를 반환하는 것이 원칙이다.

### 7.3 탐색 깊이

| 항목 | 현재 상태 | 정책 상태 |
|---|---|---|
| 깊이 전달 방식 | 호출자가 `SearchOptions.depth`로 지정 | **[확정]** |
| 브라우저 기본 깊이 | 아직 클라이언트 미연결 | **[제안]** 깊이 3 |
| 셀프플레이 깊이 | 하네스 미구현 | **[제안]** 명령행 인자 |

깊이가 높을수록 더 먼 수를 보지만 노드 수와 대기 시간이 커진다. 기본 깊이는 실제 브라우저에서 응답 시간과 수 품질을 측정한 뒤 확정한다.

### 7.4 수 정렬 우선순위

| 수 종류 | 정렬 점수 | 상태 | 의미 |
|---|---:|---|---|
| 열린 슛 | 100 | **[실험 중]** | 득점 가능성이 높은 강제 수를 먼저 탐색 |
| 막힌 슛 | 60 | **[실험 중]** | 선방으로 소유권이 바뀌는 수를 다음으로 탐색 |
| 스틸 | 50 | **[실험 중]** | 즉시 소유권을 바꾸는 수 |
| 패스 | 30 | **[실험 중]** | 공 위치와 소유를 바꾸는 수 |
| 일반 이동 | 0 | **[실험 중]** | 나머지 위치 변화 |

이 점수는 국면 평가 가중치가 아니다. **탐색 순서만 정하고 최선 수는 재귀 평가 결과로 결정한다.** 따라서 100점 열린 슛이 항상 50점 스틸보다 좋은 수라는 뜻이 아니다.

같은 정렬 점수에서는 `legalMoves()`가 생성한 원래 순서를 유지한다. 평가 점수까지 같으면 먼저 정렬된 수가 `best`로 남아 동점을 결정론적으로 처리한다.

### 7.5 탐색 결과

```ts
interface SearchResult {
  best: Move | null;
  score: number;
  values: Array<{ move: Move; score: number }>;
  nodes: number;
  depth: number;
  ms: number;
}
```

- `best`: 현재 탐색에서 가장 높은 점수의 수
- `score`: 루트 현재 팀 관점의 최선 점수
- `values`: 모든 루트 후보와 점수. 블런더 판정의 근거다.
- `nodes`: 재귀에서 방문한 하위 상태 수
- `depth`: 요청한 탐색 깊이
- `ms`: 측정된 실행 시간. 게임 결정에는 사용하지 않는다.

## 8. Lv.1 평가 정책

### 8.1 평가 공식

현재 평가는 특정 `perspective` 팀 관점의 숫자 하나를 반환한다.

```text
E(state, perspective)
  = 득점 차 가치
  + 공 상태 가치
  + 전체 기물 위치 가치
```

양수는 관점 팀에게 유리하고, 음수는 상대에게 유리하다. 대칭 국면에서 관점을 바꾸면 부호가 반전되어야 한다.

### 8.2 전체 가중치 표

| ID | 평가 항목 | 현재 값 | 적용 방식 | 상태 |
|---|---|---:|---|---|
| EV-01 | 골 차이 | `10,000 / 골` | `(내 득점 - 상대 득점) × 10,000` | **[실험 중]** |
| EV-02 | 공 소유 기본값 | `140` | 소유 팀에 더하고 상대 관점에는 뺌 | **[실험 중]** |
| EV-03 | 공 소유자 전진도 | `9 / 칸` | 소유자의 공격 방향 진행 칸 × 9 | **[실험 중]** |
| EV-04 | 열린 슛 경로 | `+450` | 현재 공 소유자에게 막히지 않은 유효 슛이 하나라도 있으면 적용 | **[실험 중]** |
| EV-05 | 인접 스틸 위협 | `-170` | 공 소유자 상하좌우에 상대 기물이 하나라도 있으면 적용 | **[실험 중]** |
| EV-06 | 루즈볼 접근성 | `30 / 거리 차` | 양 팀 최소 체비쇼프 거리 차 × 30 | **[실험 중]** |
| EV-07 | FW 전진 위치 | `3 / 칸` | 모든 FW의 공격 방향 진행 칸 × 3 | **[실험 중]** |
| EV-08 | MF 전진 위치 | `1.5 / 칸` | 모든 MF의 공격 방향 진행 칸 × 1.5 | **[실험 중]** |
| EV-09 | DF·GK 전진 위치 | `0` | 별도 위치 보너스 없음 | **[실험 중]** |

이 값들은 `reference/prototype.html`에서 작동을 검증한 휴리스틱을 이식한 것이다. 현재 코드와 테스트에 존재하지만 셀프플레이와 사용자 경기로 밸런스가 검증되지 않았으므로 모두 **[실험 중]**이다.

### 8.3 공 소유 평가

공이 held라면 다음 식을 사용한다.

```text
소유 가치
  = 140
  + 소유자 전진 칸 × 9
  + 열린 슛이 있으면 450
  - 인접 상대가 있으면 170
```

소유 팀이 관점 팀이면 이 값을 더하고 상대 팀이면 뺀다.

의도와 위험:

| 항목 | 의도 | 확인해야 할 위험 |
|---|---|---|
| 기본 140 | 루즈볼보다 안정적 소유를 선호 | 의미 없는 소유 유지가 공격보다 과대평가될 수 있음 |
| 전진 9 | 상대 골대 쪽 소유를 선호 | 측면·수비적 재배치 가치가 과소평가될 수 있음 |
| 열린 슛 450 | 즉시 득점 위협을 강하게 선호 | 슛의 실제 장기 가치보다 과도할 수 있음 |
| 위협 -170 | 빼앗길 위험을 반영 | `noSteal = 1` 보호 중에도 동일하게 감점하는 현재 동작이 부정확할 수 있음 |

특히 EV-05는 실제 스틸 가능 여부를 확인하지 않는다. 보호 턴에도 상대가 인접하면 위험으로 감점한다. 이는 단순 압박을 표현하는 의도일 수 있지만 현재는 명시적으로 검증되지 않은 **[실험 중]** 정책이다.

### 8.4 루즈볼 평가

공이 loose라면 각 팀에서 공에 가장 가까운 기물의 체비쇼프 거리를 구한다.

```text
home 관점 루즈볼 가치
  = (away 최소 거리 - home 최소 거리) × 30
```

away 관점에서는 부호를 반전한다.

체비쇼프 거리 `max(|dx|, |dy|)`는 8방향 한 칸 이동을 근사한다. 하지만 실제 역할별 이동은 서로 다르므로 정확한 도달 턴이 아니다.

- FW 나이트 이동을 정확히 반영하지 않는다.
- DF의 대각선 이동 불가를 반영하지 않는다.
- GK 박스 제한을 반영하지 않는다.
- 경로를 막는 다른 기물을 반영하지 않는다.

현재 방식은 계산이 빠르고 대칭적이라는 장점이 있다. 정확한 역할별 최단 수 계산으로 교체할지는 셀프플레이 성능과 수 품질을 측정한 뒤 결정한다.

### 8.5 위치 평가

공과 별도로 모든 FW와 MF의 공격 방향 전진도를 평가한다.

```text
기물 위치 가치
  = Σ(팀 부호 × 공격 방향 진행 칸 × 역할 가중치)

FW 가중치 = 3
MF 가중치 = 1.5
DF, GK 가중치 = 0
```

의도는 공격 역할이 전진 공간을 차지하도록 유도하는 것이다. 수비 라인 유지, 중앙 장악, 패스 연결성은 현재 직접 평가하지 않는다.

### 8.6 골 가치의 상대적 크기

한 골은 10,000점이다. 비교를 위해 보드 끝까지 전진한 한 팀의 FW 위치 보너스 최대는 `12 × 3 = 36`, MF는 `12 × 1.5 = 18`이다. 공 소유자가 최대 전진하고 열린 슛을 가지면 기본 소유 항은 대략 `140 + 108 + 450 = 698`이다.

따라서 현재 설계에서는 한 골이 위치·소유상의 일반적인 차이보다 압도적으로 중요하다. 이는 실제 득점을 다른 휴리스틱보다 우선하려는 의도이며, 최소 한 골 우위가 평가 부호를 뒤집지 않는지 테스트로 계속 보호해야 한다.

## 9. 분석 UI 정책

분석 UI는 아직 본편에 구현되지 않았다. 아래 값은 프로토타입에서 검증된 현재 **[실험 중]** 기준이다.

### 9.1 평가값의 승률 표시

```text
추정 승률 = 1 / (1 + exp(-평가값 / 900))
```

| 평가값 | 표시되는 추정 승률 |
|---:|---:|
| `-1,800` | 약 11.9% |
| `-900` | 약 26.9% |
| `0` | 50.0% |
| `+900` | 약 73.1% |
| `+1,800` | 약 88.1% |

분모 900은 곡선의 민감도를 정한다. 이 값은 실제 경기 결과로 통계 보정한 확률이 아니다. UI에서는 검증 전까지 **“승률”보다 “추정 승률”**로 표기해야 한다.

골 가치가 10,000점이라 한 골 차이는 이 공식에서 거의 100% 또는 0%로 포화된다. 경기 중 역전 가능성을 보여주고 싶다면 골 가치, 승률 스케일, 남은 턴을 함께 고려한 별도 보정이 필요하다.

### 9.2 수 품질 판정

사람 차례 시작 시 모든 루트 후보를 분석하고 다음 값을 계산한다.

```text
delta = 최선 수 점수 - 실제로 둔 수 점수
```

| delta 범위 | 판정 | 상태 |
|---:|---|---|
| `< 40` | 최선 | **[실험 중]** |
| `40..149` | 좋은 수 | **[실험 중]** |
| `150..349` | 부정확 | **[실험 중]** |
| `350..699` | 실수 | **[실험 중]** |
| `>= 700` | 블런더 | **[실험 중]** |

경계값은 현재 평가 스케일에 종속된다. 평가 가중치를 바꾸면 같은 수의 delta도 달라질 수 있으므로 EV 가중치와 판정 임계값을 독립적으로 조정하면 안 된다.

검증 기준:

- 골을 놓치는 수가 실수 또는 블런더로 분류되는가?
- 의미가 거의 같은 동점 수가 최선 또는 좋은 수로 남는가?
- 게임 초반의 작은 위치 차이를 과도하게 블런더로 부르지 않는가?
- 탐색 깊이가 달라져도 판정이 지나치게 흔들리지 않는가?

### 9.3 판정 문구

표시 문자열은 `content/strings.json`의 다음 키를 사용한다.

```text
best        최선
good        좋은 수
inaccuracy  부정확
mistake     실수
blunder     블런더!
```

판정 계산은 엔진·분석 정책이고, 문구와 어조는 콘텐츠 정책이다. 문자열 변경이 수치 판정을 바꾸면 안 된다.

## 10. 코드와 content 설정의 관계

### 10.1 현재 불일치

`content/pieces.json`에는 다음 값이 선언돼 있다.

```text
GK range 1
DF range 2
MF range 2
FW knight range 1
passDirections 8
stealProtectionTurns 1
maxTurns 60
```

그러나 현재 `src/engine/rules.ts`는 이 JSON을 읽지 않는다. 같은 값을 코드에 하드코딩하고 있어 JSON을 변경해도 실제 게임 규칙은 바뀌지 않는다.

| 항목 | JSON 선언 | 현재 코드 | 런타임 기준 |
|---|---:|---:|---|
| GK 이동 | 1 | 1 | 코드 |
| DF 이동 | 2 | 2 | 코드 |
| MF 이동 | 2 | 2 | 코드 |
| 패스 방향 | 8 | 8 | 코드 |
| 스틸 보호 | 1 | 1 | 코드 |
| 최대 턴 | 60 | 60 | 코드 |

현재 값은 우연히 일치하지만 연결된 것은 아니다.

### 10.2 목표 정책

**[제안]** 룰 설정을 순수 데이터 객체로 만들어 엔진 함수에 주입하고 `content/pieces.json`은 클라이언트·도구 계층에서 파싱한다.

```text
content/pieces.json
  → 설정 검증
  → RuleConfig 생성
  → createInitialState(config)
  → legalMoves(state, config)
  → applyMove(state, move, config)
```

엔진이 직접 파일을 읽거나 브라우저 import에 의존해서는 안 된다. 기본 설정은 코드에 보존해 테스트와 Node 셀프플레이가 명시적인 설정 없이도 같은 기준으로 실행되게 한다.

설정 주입이 구현되기 전까지는 `content/pieces.json`을 밸런스 조정의 실제 입력으로 설명하지 않는다.

## 11. 불변 조건과 검증 정책

### 11.1 반드시 유지할 불변 조건

- 모든 기물 좌표는 보드 안에 있다.
- 두 기물이 같은 칸을 점유하지 않는다.
- held 공은 존재하는 기물 ID를 가리킨다.
- loose 공은 보드 안 좌표를 가진다.
- 한 수는 현재 차례 팀의 합법 수 목록에서 선택한다.
- `applyMove()`는 입력 상태를 변경하지 않는다.
- 득점 후 실점 팀이 킥오프한다.
- `turn >= maxTurns`에서 합법 수와 최선 수가 없다.
- 동일 상태·깊이·평가 함수는 동일한 논리적 탐색 결과를 낸다.
- 측정 시간 `ms`만 결정론 비교에서 제외한다.

### 11.2 현재 자동 테스트 범위

1. 초기 4대4 배치와 home MF 킥오프
2. 보드 범위와 기물 좌표 중복

## 12. 정책 변경 절차

### 12.1 고정 규칙 변경

1. 변경할 정책과 플레이어 경험상의 이유를 적는다.
2. **[확정]**을 바로 수정하지 않고 변경 후보를 **[제안]**으로 추가한다.
3. 영향을 받는 합법 수, 상태 전이, 평가, UI, content 키를 나열한다.
4. 기존 동작을 보여주는 테스트와 새 기대 동작 테스트를 비교한다.
5. 사용자 승인을 받는다.
6. 코드를 구현하고 `npm run check`를 실행한다.
7. 대표 경기 또는 퍼즐로 사람이 결과를 확인한다.
8. 승인된 후보를 **[확정]**으로 승격하고 변경 기록을 남긴다.

### 12.2 실험 가중치 변경

1. 가설을 한 문장으로 적는다. 예: “열린 슛 보너스 450이 지나치게 커 봇이 무리한 슛 진입을 선호한다.”
2. 변경 전 기준 셀프플레이 결과와 대표 국면 점수를 기록한다.
3. 한 번에 가능한 한 하나의 가중치만 바꾼다.
4. 변경 후 같은 조건을 재실행한다.
5. 승률뿐 아니라 평균 골, 평균 수, 분기 수, 대표 수 선택을 비교한다.
6. 사용자 플레이에서 전략이 더 이해하기 쉬워졌는지 확인한다.
7. 채택 또는 롤백 결정을 실험 기록에 남긴다.

### 12.3 상태 승격 기준

**[실험 중] → [확정]** 승격에는 다음이 필요하다.

- 값의 의도를 한 문장으로 설명할 수 있다.
- 자동 테스트가 관련 불변 조건을 보호한다.
- 셀프플레이 또는 고정 국면 비교 결과가 있다.
- 최소 한 번의 실제 사용자 플레이에서 치명적인 이상 행동이 없다.
- 해당 값과 연결된 UI 설명이 오해를 만들지 않는다.

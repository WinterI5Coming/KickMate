## 2. 제품 목표

KickMate는 **교대 턴제 축구 보드게임에 자체 엔진 분석을 결합한 “축구의 chess.com”**이다.

### 제출 가능한 최소 제품

사용자가 브라우저에서 다음 흐름을 끊김 없이 완료할 수 있어야 한다.

```text
게임 시작
  → 합법 수를 선택해 home 팀으로 플레이
  → Web Worker의 봇이 away 팀 최선 수를 계산해 응수
  → 득점·킥오프·턴 교대·3골 또는 60 ply 종료
  → 경기 결과 표시
  → 실수와 블런더를 모은 경기 후 리뷰
  → 해당 국면과 엔진 최선 수 확인
```

### 핵심 성공 기준

- 봇과 3골 선취 또는 최대 60 ply 경기를 크래시 없이 완주할 수 있다.
- 게임 규칙과 엔진 탐색은 같은 입력에 같은 결과를 내는 결정론적 시스템이다.
- 탐색이 UI 메인 스레드를 막지 않는다.
- 사람이 둔 수를 최선 수와 비교해 최선·좋은 수·부정확·실수·블런더로 판정한다.
- 경기 종료 후 블런더와 실수 국면을 다시 볼 수 있다.
- `npm run check`와 `npm run build`가 통과한다.
- 팀원이 접근할 수 있는 웹 배포 URL이 존재한다.

### 우선순위

1. 봇전 완주
2. 경기 후 블런더 리뷰와 최선 수 설명
3. 안정적인 배포와 검증 자동화
4. 퍼즐 온보딩과 핫시트
5. 콘텐츠·연출 품질
6. 학습 평가, LLM 코치, 온라인 대전은 제출 최소 범위 밖의 확장 기능

## 3. 확정 설계 원칙

| ID | 원칙 | 구현에 미치는 영향 |
|---|---|---|
| C1 | 엔진에서 무작위 호출을 사용하지 않는다 | `Math.random()`, 시간 기반 선택, 불안정한 순회 순서에 의존하지 않는다 |
| C2 | `src/engine/`은 순수 TypeScript로 유지한다 | DOM, Canvas, Worker 전역, `fetch`, 파일시스템을 참조하지 않는다 |
| C3 | 탐색은 Worker 프로토콜을 통해 호출한다 | 클라이언트가 `search()`를 직접 실행하지 않는다 |
| C4 | 상태 전이는 입력을 변경하지 않는다 | `applyMove(state, move)`는 새로운 `GameState`를 반환한다 |
| C5 | 하나의 엔진을 모든 실행 환경에서 재사용한다 | 브라우저 대국, 분석, 퍼즐 검산, Node 셀프플레이가 같은 룰·탐색을 사용한다 |
| C6 | 콘텐츠와 화면 문구를 코드에서 분리한다 | `content/`의 JSON을 검증하고 점진적으로 런타임에 연결한다 |
| C7 | 완료 전 통합 게이트를 통과한다 | `npm run check`와 필요한 사용자 시나리오 검증을 수행한다 |
| C8 | 기존 검증된 룰을 임의로 개선하지 않는다 | 수치 변경은 셀프플레이 측정과 명시적 결정을 근거로 한다 |

## 4. 시스템 설계

### 4.1 계층 구조

```text
브라우저 사용자
  ↓ 클릭·터치
src/client/
  ├─ 화면 상태와 대국 흐름
  ├─ Canvas 렌더링
  ├─ 입력을 Move로 변환
  └─ 분석·리뷰 UI
  ↓ analyze / legalMoves 메시지
src/worker/
  ├─ 요청 ID 매칭
  ├─ 오류 직렬화
  └─ 엔진 호출 어댑터
  ↓
src/engine/
  ├─ types.ts       상태와 수의 공용 계약
  ├─ rules.ts       초기 상태, 합법 수, 상태 전이
  ├─ eval/lv1.ts    휴리스틱 평가
  └─ search.ts      네가맥스 + 알파베타 탐색

content/ ──→ 클라이언트 문구·테마·퍼즐·룰 설정
tools/   ──→ 같은 엔진을 사용한 검증·셀프플레이
```

### 4.2 핵심 데이터 흐름

한 수의 진행:

```text
GameState
  → legalMoves(state)
  → 사용자가 Move 선택
  → applyMove(state, move)
  → 새 GameState 렌더
  → 봇 차례이면 Worker analyze 요청
  → SearchResult.best 적용
```

분석과 블런더 판정:

```text
사람 차례 시작 국면
  → Worker가 모든 루트 후보 values 계산
  → 사람이 둔 수의 score 조회
  → best.score - played.score = delta
  → 임계값으로 수 품질 판정
  → 기보와 리뷰 데이터에 원래 국면·수·최선 수 저장
```

### 4.3 모듈 경계

- `client`는 화면과 사용자 흐름을 소유하지만 규칙을 재구현하지 않는다.
- `worker`는 메시지 중계만 담당하며 별도 게임 상태를 소유하지 않는다.
- `engine`은 화면을 모르고 `GameState → Move[]`, `GameState × Move → GameState`, `GameState → SearchResult`만 제공한다.
- `content`는 비개발자도 수정할 수 있는 데이터 영역이며, 잘못된 값은 런타임보다 `npm run validate`에서 먼저 차단한다.
- `tools`는 브라우저 코드를 복제하지 않고 엔진 공개 API를 직접 사용한다.

### 5.3 구현 완료 항목 상세

#### 엔진 공용 타입 — `src/engine/types.ts`

- 13×9 보드 상수와 `home | away` 팀을 정의했다.
- GK, DF, MF, FW 기물과 고유 ID·좌표 계약을 정의했다.
- 공을 `held`와 `loose`로 분리해 모순된 소유·좌표 상태를 타입으로 방지했다.
- `GameState`에 턴, 최대 턴, 기물, 공, 스틸 보호 카운터, 점수를 포함했다.
- 이동, 패스, 슛, 스틸을 판별 가능한 `Move` 유니온으로 정의했다.
- `SearchResult`가 최선 수뿐 아니라 모든 루트 후보의 점수를 `values`로 반환하도록 확장했다.

#### 룰·상태 전이 — `src/engine/rules.ts`

- 양 팀 4기물의 미러 초기 배치와 home MF 센터 킥오프를 구현했다.
- GK 박스 이동, DF 직선 이동, MF 8방향 이동, FW 나이트 이동을 구현했다.
- 8방향 최대 6칸 패스와 첫 접촉 기물에 따른 패스 차단·연결을 구현했다.
- 최대 7칸 슛, 골문 3개 행, 경로 첫 기물 선방, 빈 경로 득점을 구현했다.
- 인접 스틸과 스틸·선방 직후 한 수 보호를 구현했다.
- 득점 후 초기 배치 복원과 실점 팀 킥오프를 구현했다.
- 60수 도달 시 합법 수가 생성되지 않도록 했다.
- `applyMove()`가 입력 상태와 중첩 객체를 변경하지 않도록 복제 기반으로 구현했다.

#### Lv.1 평가 — `src/engine/eval/lv1.ts`

- 득점 차에 가장 큰 가중치를 적용했다.
- 공 소유, 공격 방향 전진도, 열린 슛 경로를 평가한다.
- 상대 스틸 위협을 감점한다.
- 루즈볼일 때 양 팀의 접근 거리를 비교한다.
- MF와 FW의 위치 전진 보너스를 적용한다.
- 평가 관점 팀에 따라 부호가 일관되게 반전된다.

#### 탐색 — `src/engine/search.ts`

- 네가맥스와 알파베타 가지치기를 구현했다.
- 득점 슛, 선방 슛, 스틸, 패스, 이동 순으로 안정적인 후보 정렬을 사용한다.
- 같은 상태와 깊이는 같은 최선 수와 후보 점수를 반환한다.
- 분석 UI가 사용할 모든 루트 후보 점수, 노드 수, 깊이, 소요 시간을 반환한다.
- 종료 상태와 깊이 0을 처리한다.

#### Worker 경계 — `src/worker/`

- `protocol.ts`에 `analyze`와 `legalMoves` 요청 및 응답 타입이 있다.
- 각 요청은 `requestId`를 포함해 비동기 응답을 구분할 수 있다.
- `engine.worker.ts`가 탐색과 합법 수 생성을 엔진에 위임한다.
- 예외를 문자열 `error` 응답으로 변환한다.

#### 자동 검증 — `src/engine/rules.test.ts`

현재 11개 테스트가 다음을 보호한다.

1. 4대4 초기 배치와 home MF 킥오프
2. 기물의 보드 범위와 좌표 중복 방지
3. 초기 국면 합법 수 존재
4. 이동·패스 목적지의 보드 범위
5. 상태 전이의 입력 불변성
6. 빈 슛 경로의 득점과 킥오프 리셋
7. 슛 경로 첫 기물의 선방과 소유권 이전
8. 스틸 직후 한 수 재스틸 방지
9. 대칭 국면 평가 부호
10. 루트 후보 점수를 포함한 탐색 결정론

## 6. 부분 구현과 현재 간극

### 6.1 클라이언트 화면

`src/client/main.ts`는 보드, 격자, 기물, 루즈볼을 한 번 그린다. 다음 간극 때문에 아직 게임이 아니다.

- `render()` 내부에서 매번 초기 상태를 새로 만들어 진행 상태를 유지하지 못한다.
- 초기 공은 기물이 소유한 `held` 상태라 화면에 보이지 않는다.
- Canvas 클릭을 보드 좌표와 수 선택으로 변환하지 않는다.
- 선택 기물, 합법 목적지, 마지막 수, 탐색 중 상태를 표시하지 않는다.
- 점수, 현재 팀, 남은 턴, 경기 종료 결과를 표시하지 않는다.

### 6.2 Worker 연결

Worker 파일은 준비됐지만 클라이언트에 다음 요소가 없다.

- `new Worker(new URL(...), { type: "module" })` 생성
- 증가하는 `requestId`
- 응답 대기 Promise 저장소
- `analysis`, `legalMoves`, `error` 응답 분기
- Worker 종료와 예상하지 못한 오류 처리

### 6.3 content 데이터

- `theme.json`: 보드와 팀 색상에 사용 중
- `strings.json`: 앱 제목만 사용 중
- `pieces.json`: 검증만 하고 엔진 룰에는 미주입
- `puzzles/*.json`: 구조 검증만 하고 게임·해결 가능성 검산에는 미연결

### 6.4 저장소 상태

S1 엔진 이식과 설명 문서는 `0bc3d01`까지 로컬 커밋돼 있다. 아직 Git 원격이 없어 원격 백업, PR·CI 실행 이력, 다른 환경에서의 재현 검증은 없다.

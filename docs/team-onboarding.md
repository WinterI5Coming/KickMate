# KickMate 팀원 온보딩 가이드

> 이 문서는 KickMate를 함께 만드는 팀원이 코드를 읽지 않고도 게임의 목적, 핵심 기능, 동작 방식, 현재 상태와 자신의 의사결정 범위를 이해하기 위한 안내서다.
> 기술 구현의 상세 내용보다 “무엇을 만들고 있으며 어떤 경험을 제공해야 하는가”에 집중한다.

- 대상: KickMate 팀원 3명
- 최초 작성일: 2026-08-17
- 마지막 갱신일: 2026-08-22
- 상세 계획: [프로젝트 설계·구현 계획](./project-plan.md)
- 상세 규칙과 엔진 수치: [게임 정책·엔진 원리](./game-policy.md)
- 코드의 현재 상태: [현재 구현 상태](./current-state.md)

## 1. 가장 먼저 알아야 할 것

### 한 줄 소개

**KickMate는 한 팀이 세 행동을 조합해 압박·탈취·패스·슛 장면을 만드는 짧은 턴제 축구 게임이다.**

### 우리가 만들고 싶은 경험

사용자는 짧은 한 판에서 공수 선택을 연속으로 조합하고 그 결과를 즉시 확인한다.

```text
세 행동으로 공격 또는 압박 장면을 만든다
  → 패스·슛·탈취 결과를 본다
  → 상대 팀의 세 행동에 대응한다
  → 5~8분 안에 경기를 끝낸다
  → 바로 다른 선택으로 다시 플레이한다
```

KickMate의 현재 핵심은 축구처럼 보이는 보드에서 사건이 자주 일어나는 한 판의 재미다.
경기 후 엔진 복기는 핵심 경기가 재미있다고 검증된 뒤 붙일 차별화 후보다.

---

## 2. 왜 이 게임을 만드는가

기존 축구 게임은 대체로 빠른 조작, 선수 능력치, 실시간 액션에 집중한다. KickMate는 다른 방향을 선택한다.

- 반사 신경보다 판단을 중요하게 만든다.
- 제한된 행동을 어디에 쓸지 선택하게 한다.
- 확률을 쓰더라도 위험과 유리한 조건을 실행 전에 읽을 수 있게 한다.
- 축구의 패스, 공간, 압박, 슛 기회를 작은 보드에서 읽게 만든다.
- 같은 경기 시드는 다시 재현할 수 있게 해 테스트와 분석이 가능하게 만든다.

### 우리 게임이 다른 점

| 일반적인 축구 게임 | KickMate |
|---|---|
| 실시간 조작 | 팀 턴마다 제한된 행동을 조합 |
| 숨겨진 결과 | 실행 전 경로와 위험을 표시 |
| 긴 시즌과 육성 | 5~8분짜리 단판 우선 |
| 빠른 반응이 중요 | 짧은 계획과 위험 관리가 중요 |
| AI 결과 재현이 어려움 | 동일 시드와 상태의 결과를 재현 |

---

## 3. 누구를 위한 게임인가

### 주요 사용자

- 축구를 좋아하지만 실시간 축구 게임 조작은 부담스러운 사람
- 보드게임처럼 몇 가지 행동을 조합하는 게임을 좋아하는 사람
- 긴 성장 없이 짧은 규칙으로 바로 한 판 하고 싶은 사람
- 같은 상황에서 다른 공격 루트를 시험하는 것을 좋아하는 사람

### 처음 플레이한 사용자가 느껴야 하는 것

1. “한 턴에 세 행동을 어떻게 조합할지 고르는 게임이구나.”
2. “수비수가 붙으면 공을 지키거나 패스해야 하는구나.”
3. “막힌 슛도 리바운드로 다음 장면이 생기는구나.”
4. “짧아서 다른 전술로 바로 다시 해볼 수 있겠다.”

처음 5분 안에 최소한 1~3번까지 이해할 수 있어야 한다.

## 4. 사용자가 실제로 하는 일

한 경기에서 사용자는 home 팀을 맡고 봇은 away 팀을 맡는다.

```text
내 팀 턴
  → 행동 포인트 3 획득
  → 이동·패스·슛·스틸·버티기를 조합
  → 포인트를 다 쓰거나 턴 종료

봇 차례
  → 엔진이 행동 조합을 탐색
  → 세 행동을 순서대로 적용

최대 60행동까지 반복
  → 점수로 승·패·무 결정
  → 경기 결과 확인
```

### 한 수에 할 수 있는 행동

| 행동 | 의미 |
|---|---|
| 이동 | 기물을 빈 칸으로 움직인다 |
| 패스 | 공 소유자가 같은 직선이나 대각선 방향으로 공을 보낸다 |
| 슛 | 골문을 향한 유효한 경로로 슛한다 |
| 스틸 | 공 소유자와 8방향으로 붙은 기물이 공을 빼앗는다 |
| 버티기 | 압박받는 공 소유자가 행동을 써서 다음 이동을 가능하게 한다 |

현재 워킹 트리는 M2.6A를 구현했다. 한 팀은 행동 포인트 3개를 쓰고, 같은 선수는 팀
턴마다 최대 두 번 행동한다. 남은 행동은 한 번 이상 행동한 뒤 턴 종료로 버릴 수 있다.
실제 브라우저·모바일 플레이 검증은 아직 남아 있다.

## 5. 게임 규칙의 큰 그림

이 절은 현재 M2.6A 6대6 런타임을 설명한다. 예외와 정확한 좌표는
`game-policy.md`를 기준으로 하며, 설계 배경은 [FT&G 벤치마킹 경기 코어 개편](./superpowers/specs/2026-08-22-ftg-inspired-match-core-design.md)에 남아 있다.

### 보드와 팀

- 보드는 가로 13칸, 세로 9칸이다.
- home과 away 두 팀이 있다.
- 각 팀은 GK 1, DF 2, MF 2, FW 1을 가진다.
- 총 기물 수는 12개다.
- home은 오른쪽, away는 왼쪽 골대를 향해 공격한다.

### 이동

| 역할 | 쉽게 설명하면 |
|---|---|
| GK | 자기 골키퍼 박스 안에서 8방향 1칸 이동 |
| DF·MF·FW | 공통으로 8방향 1칸 이동 |

### 공

공은 다음 두 상태 중 하나다.

- 특정 기물이 소유한다.
- 아무도 소유하지 않은 채 보드의 한 칸에 놓인다.

공을 가진 기물이 움직이면 공도 같이 움직인다. 루즈볼이 있는 칸으로 기물이 이동하면 그 기물이 공을 가진다.

### 패스

- 공을 가진 기물만 패스할 수 있다.
- 6칸 안의 받을 아군을 직접 고른다.
- 경로에서 처음 만난 기물이 아군이면 그 기물에게 전달한다.
- 경로에서 처음 만난 기물이 상대면 그 방향은 막힌다.
- 첫 기물이 아군이면 그 기물이 받고, 상대면 가로챈다.

### 슛과 골

- 공을 가진 기물만 슛할 수 있다.
- 골문까지의 거리가 최대 7칸일 때 유효한 슛 경로가 생길 수 있다.
- 슛 경로에 기물이 없으면 골이다.
- 슛은 아군 기물을 통과하고 첫 상대 기물만 차단자로 본다.
- 상대 GK의 차단은 GK 소유와 스틸 보호로, 상대 필드 선수의 차단은 인접 빈 칸의 결정론적 루즈볼 리바운드로 처리한다.

### 스틸

- 상대 공 소유자와 8방향으로 붙어 있는 기물이 스틸할 수 있다.
- 스틸은 확률 없이 항상 성공한다.
- 스틸·패스 차단·GK 선방·직접 소유권 획득 뒤에는 `stealProtection`이 공을 잃은 팀의 다음 원자 행동 1회 동안만 재스틸을 막는다. 공격자 2명이 공 소유자에 인접하면 보호를 즉시 무시한다.

### 득점과 종료

- 골이 나면 점수가 1점 오른다.
- 모든 기물이 기본 위치로 돌아간다.
- 실점한 팀 MF가 센터에서 공을 가지고 다시 시작한다.
- 총 60수가 끝나면 다득점 팀이 승리한다.
- 점수가 같으면 무승부다.

## 6. 엔진은 무엇을 하는가

엔진은 화면을 그리는 프로그램이 아니라, 현재 상황을 보고 가능한 행동과 좋은 행동을 계산하는 게임의 두뇌다.

### 엔진의 네 가지 역할

1. 현재 상황에서 가능한 합법 수를 만든다.
2. 선택한 수를 적용해 새로운 경기 상태를 만든다.
3. 국면이 어느 팀에게 얼마나 유리한지 평가한다.
4. 여러 수 앞을 읽어 최선 수를 고른다.

### 엔진이 평가하는 것

현재 Lv.1 엔진은 다음 요소를 본다.

- 득점 차이
- 어느 팀이 공을 가지고 있는지
- 공이 상대 골대 쪽으로 얼마나 전진했는지
- 바로 슛할 수 있는 경로가 있는지
- 공 소유자가 스틸 위협을 받는지
- 루즈볼에 어느 팀이 더 가까운지
- MF와 FW가 얼마나 전진했는지

각 요소에는 현재 임시 가중치가 들어가 있다. 이 수치는 작동하는 프로토타입을 만들기 위해 정한 값이며 아직 최종 밸런스가 아니다.

### 팀원이 결정해야 하는 것과 개발자가 결정해야 하는 것

| 팀원이 결정 | 개발자가 결정 |
|---|---|
| 어떤 행동이 더 중요한가 | 중요도를 숫자로 어떻게 표현할지 |
| 어떤 상황을 실수로 볼지 | 평가 함수와 임계값 구현 방식 |
| 게임 규칙의 예외 상황 | 상태와 타입을 표현하는 코드 구조 |
| 봇이 어떤 성향이어야 하는지 | 탐색 알고리즘과 성능 최적화 |
| 사용자에게 무엇을 보여줄지 | Worker, Canvas, UI 구현 |

예를 들어 팀원은 “열린 슛은 단순 공 소유보다 훨씬 중요하지만 실제 득점보다는 낮아야 한다”고 결정한다. 개발자는 이를 평가값과 테스트로 옮긴다.

## 7. 경기 후 분석이 제공할 기능 `[후순위]`

경기 후 복기는 보존된 차별화 후보지만 M2.6A와 확률·스탯 검증보다 뒤에 구현한다.

### 수 판정

엔진은 사람이 둔 수를 그 국면의 최선 수와 비교한다.

```text
최선 수의 점수 - 실제로 둔 수의 점수 = 손해 본 평가값
```

이 차이에 따라 다음과 같이 분류한다.

- 최선
- 좋은 수
- 부정확
- 실수
- 블런더

현재 분류 기준 숫자는 임시값이다. 어떤 상황을 실제 블런더로 불러야 하는지는 팀이 대표 장면을 보고 확정해야 한다.

### 경기 중 제공할 정보

- 현재 점수와 차례
- 엔진의 추정 평가
- 추정 승률
- 기보와 각 수의 판정
- 요청 시 최선 수 힌트

### 경기 후 제공할 정보

- 경기 결과
- 실수와 블런더 목록
- 당시 경기 상태
- 사용자가 둔 수
- 엔진이 추천한 최선 수
- 두 수의 평가 차이

목표는 사용자를 꾸짖는 것이 아니라 “다음에는 무엇을 보면 되는지” 알려주는 것이다.

## 8. 제공할 게임 모드

| 우선순위 | 모드 | 설명 | 현재 목표 |
|---:|---|---|---|
| 1 | 봇전 | 엔진과 한 경기 플레이하고 복기 | 반드시 구현 |
| 2 | 핫시트 | 한 기기에서 두 사람이 교대 | 구현 목표 |
| 3 | 퍼즐 | 제한 턴 안에 골 넣기 | 온보딩용으로 구현 목표 |
| 4 | 온라인 대전 | 다른 기기 사용자와 경기 | 제출판 이후 로드맵 |

### 제출판에 반드시 필요한 것

- 봇과 한 경기 완주
- 경기 후 블런더 리뷰
- 최선 수 확인
- 실행 가능한 웹 빌드

### 제출판에서 우선 잘라낼 기능

일정이 부족하면 다음 순서로 제외한다.

1. LLM 코치
2. 학습 기반 Lv.2 평가
3. 실경기 데이터 기능
4. 퍼즐 개수 축소
5. 부가 연출 축소

봇전 완주와 경기 후 리뷰는 제외하지 않는다.

## 10. 팀의 역할

### 개발·구현 책임자

- 모든 TypeScript 구현
- 엔진, Worker, 화면, 입력, 테스트
- 확정된 정책을 코드로 이식
- 평가 우선순위를 실제 수치로 변환
- CI, 배포, 통합
- 기술적으로 불가능하거나 일정상 위험한 정책에 대해 대안을 제시

개발 책임자는 사용자와 팀이 확정하지 않은 게임 규칙을 임의로 확정하지 않는다.

### 팀원 1 — 게임 규칙 정책 책임자

이 역할은 “게임에서 어떤 일이 일어나야 하는가”를 결정한다.

- 기물 이동 규칙 검토
- 패스·슛·스틸 경계 상황 결정
- 슛 차단과 선방 정의
- 킥오프와 경기 종료 예외 결정
- 규칙을 처음 보는 사람이 이해할 수 있는지 검토
- 퍼즐에서 가르칠 공식 규칙 확정
- 플레이 결과를 보고 규칙 변경 여부 판단

코드를 작성할 필요는 없다. 결정에는 이유, 정상 예시, 경계 상황을 포함한다.

### 팀원 2 — 분석·사용자 경험 정책 책임자

이 역할은 “사용자가 게임을 어떻게 이해하고 피드백받는가”를 결정한다.

- 어떤 행동을 좋은 수와 나쁜 수로 볼지 결정
- 봇이 추구해야 할 플레이 성향 정의
- 최선·좋은 수·부정확·실수·블런더의 의미 정의
- 힌트가 보여줄 정보 결정
- 경기 후 리뷰에 필요한 정보 결정
- 추정 승률과 평가값의 표현 방식 결정
- 온보딩과 퍼즐 난이도 순서 결정
- 문구와 피드백의 어조 결정

정확한 수치와 알고리즘보다 행동의 우선순위와 사용자에게 전달될 의미를 정의한다.

---

## 11. 정책을 결정하는 방법

팀원이 정책을 제안할 때는 다음 형식을 사용한다.

```text
정책 ID:
결정할 질문:
제안하는 동작:
이유:
정상 상황 예시:
경계 상황 예시:
사용자에게 보이는 결과:
상태: 제안 / 확정
제안자:
결정일:
```

### 좋은 정책 결정의 예

```text
정책 ID: RULE-SHOT-02
결정할 질문: 슛 경로에 아군 기물이 있으면 어떻게 되는가?

제안하는 동작:
아군 기물이 슛을 막고 해당 기물이 공을 소유한다.
화면에서는 “선방”이 아니라 “슛 차단”으로 표시한다.

이유:
아군을 통과해서 슛하면 다른 경로 차단 규칙과 일관되지 않다.

정상 상황 예시:
home FW와 골대 사이에 home MF가 있으면 FW의 슛은 MF에게 막힌다.

상태: 제안
```

### 피해야 할 결정

- “그냥 더 재미있게 해 주세요.”
- “AI가 똑똑하게 움직이면 좋겠습니다.”
- “열린 슛 가중치는 450이 좋을 것 같습니다.”
- 정상 상황만 있고 예외 상황이 없는 규칙
- 이유 없이 기존 정책을 바꾸는 결정

숫자가 아니라 원하는 행동과 그 이유를 먼저 정한다.

## 12. 정책 확정과 구현 흐름

```text
팀원이 정책 제안
  → 세 명이 예시와 경계 상황 검토
  → game-policy.md에서 [확정]
  → 개발자가 실패 테스트 작성
  → 코드 구현
  → npm run check
  → 배포 또는 실행 화면 확인
  → 정책 제안자가 의도대로 동작하는지 승인
```

### 의사결정 권한

- 게임 규칙의 최종 결정: 팀원 1의 제안 + 팀 전체 합의
- 분석·사용자 경험의 최종 결정: 팀원 2의 제안 + 팀 전체 합의
- 구현 방식의 최종 결정: 개발 책임자
- 일정상 제외할 기능의 최종 결정: 팀 전체, 개발 책임자가 기술 비용 설명
- 합의되지 않은 정책: **[제안]** 상태로 유지하고 확정 규칙처럼 구현하지 않는다.

## 13. 이 문서를 읽은 뒤 확인할 질문

각 팀원은 다음 질문에 자신의 말로 답할 수 있어야 한다.

1. KickMate를 한 문장으로 설명할 수 있는가?
2. 다른 축구 게임과 무엇이 다른가?
3. 사용자는 한 차례에 무엇을 할 수 있는가?
4. 네 역할의 기물 이동 차이를 설명할 수 있는가?
5. 패스가 상대 기물에 막히는 과정을 설명할 수 있는가?
6. 슛이 골 또는 차단으로 처리되는 조건을 설명할 수 있는가?
7. 소유권 획득 뒤 1행동 유예와 2인 포위 예외가 왜 필요한지 설명할 수 있는가?
8. 엔진이 어떤 요소를 보고 국면을 평가하는지 말할 수 있는가?
9. 왜 현재 가중치와 블런더 기준이 최종값이 아닌가?
10. 봇전과 경기 후 리뷰가 왜 절대 제외할 수 없는 기능인가?
11. 자신이 결정해야 하는 정책과 개발자가 결정할 구현을 구분할 수 있는가?
12. 정책 제안에 어떤 예시와 이유가 필요한지 알고 있는가?

답하기 어려운 항목은 해당 정책을 맡기기 전에 팀에서 다시 설명한다.

## 14. 용어

| 용어 | 뜻 |
|---|---|
| ply | 한 팀이 행동 하나를 수행한 단위. KickMate의 60수는 총 60 ply다 |
| 합법 수 | 현재 규칙에서 실제로 선택할 수 있는 행동 |
| 국면 | 특정 순간의 기물, 공, 차례, 점수 전체 상태 |
| 평가값 | 엔진이 한 국면의 유불리를 숫자로 나타낸 값 |
| 최선 수 | 현재 탐색 범위에서 평가가 가장 높은 행동 |
| delta | 최선 수와 실제 수의 평가 차이 |
| 블런더 | 최선 수에 비해 매우 큰 손해를 만든 행동 |
| 결정론 | 같은 입력에 항상 같은 논리적 결과가 나오는 성질 |
| Worker | 엔진 탐색이 화면을 멈추지 않게 별도 작업 공간에서 실행하는 브라우저 기능 |
| 셀프플레이 | 봇끼리 반복 경기해 밸런스와 행동을 측정하는 도구 |
